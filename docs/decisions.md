## D-001 — Keel adopted in an existing project (brownfield)
- Date / phase: 2026-07-18 / Adoption
- Decision: Klytos CMS is brought under the Keel workflow via the adoption entry mode (`references/adoption.md`). Adoption documents reality and changes no code.
- Why: The project is mature and already released (self-updater, public GitHub releases, production installs), but had no Keel state (`docs/PROGRESS.md` did not exist) despite carrying a Keel lock and an outdated embedded skill copy.
- Alternatives rejected (and why): Treating it as a new project (would discard the as-built reality); resume mode (no state existed to resume from).
- Supersedes: none

## D-003 — Project type: web app + MCP server (both security profiles)
- Date / phase: 2026-07-18 / Adoption (as-built)
- Decision: Klytos is classified as a self-hosted web application that also exposes an MCP server. Both `references/security/web-app.md` and `references/security/mcp-server.md` apply; on any conflict the stricter rule wins.
- Why: The product's primary interface is MCP (`/mcp` JSON-RPC endpoint, OAuth 2.0, 180+ core tools) sitting on top of a full PHP admin application with authentication, 2FA, payments (x402) and encrypted data at rest.
- Alternatives rejected (and why): "MCP server" alone (ignores the admin panel, sessions, CSRF, uploads); "web app" alone (ignores the model-facing threat class: tool poisoning, injection via tool results, confused deputy).
- Supersedes: none

## D-004 — Adopted as-is: stack and conventions
- Date / phase: 2026-07-18 / Adoption (as-built)
- Decision: The existing stack and conventions are adopted as-is and are the contract for new code: PHP 8.1+ with no framework; custom `spl_autoload_register` for `Klytos\Core`; `klytos_*` snake_case global helper API; PSR-12 as adapted by `phpcs.xml` (spaces inside parentheses permitted, snake_case exempted for the helper files); manager-class architecture behind `App`; pluggable `StorageInterface` (file/database); WordPress-style hooks (`klytos_do_action` / `klytos_apply_filters`).
- Why: Adoption principle 2 — conventions are observed, not imposed. Consistency with 228 existing PHP files beats Keel's defaults.
- Alternatives rejected (and why): Migrating to Composer/PSR-4/a framework — a real option, but a user decision for a future sprint, not an adoption-time change.
- Supersedes: none

## D-006 — Adopted as-is: i18n is multi-language, base English, custom JSON mechanism
- Date / phase: 2026-07-18 / Adoption (as-built)
- Decision: The product is multi-language with English as the base language, 20 shipped locales, and a custom key-based JSON mechanism (`installer/core/i18n.php`, `__('domain.key')`), not gettext. New user-facing strings go through `__()` with a catalogue key added to all locales.
- Why: The mechanism exists, the 20 catalogues are perfectly in sync (639 keys each), and switching to gettext now would be a rewrite with no user-visible benefit.
- Alternatives rejected (and why): Migrating to gettext/`.pot` (Keel's WordPress rule does not apply — this is not a WordPress project); leaving strings hardcoded (rejected — the observed hardcoding is recorded as a gap in `docs/04-adoption-audit.md`, not as an accepted practice).
- Supersedes: none

## D-007 — Accessibility target: WCAG 2.2 AA + European Accessibility Act
- Date / phase: 2026-07-18 / Adoption step 3
- Decision: The project targets WCAG 2.2 AA as the floor (AAA where feasible) plus EN 301 549 / the European Accessibility Act, applied to **both** the admin panel and the HTML Klytos generates for its users' sites.
- Why: Klytos operates in the EU market and, critically, its users inherit the accessibility of the generated output — under the EAA the legal exposure lands on them for markup they did not write. Measured reality at adoption is ~20–25% (admin) and ~15% (generated output), so this is a target with real work behind it, not a claim.
- Alternatives rejected (and why): WCAG 2.1 AA (what the shipped `klytos-accessibility` skill already asserts — but 2.2 adds focus appearance, target size and dragging movements, which are exactly the gaps measured); generated output only (the admin is also used by people with disabilities).
- Supersedes: none

## D-010 — Assistant config package: full, for six tools
- Date / phase: 2026-07-18 / Adoption step 3

## D-011 — Model binding: default role→model map
- Date / phase: 2026-07-18 / Adoption step 3
- Decision: Abstract roles bind to models as follows, materialized in each tool's native model field using that vendor's own identifiers: `orchestrator` → the strongest available model (session driver, judgment-heavy phases); `reviewer` → mid tier (`code-reviewer`, `security-auditor`, `design-fidelity-auditor`); `mechanical` → cheapest tier (`docs-verifier`, `playground-qa`, `launch-verifier`, `a11y-auditor`, `guide-qa`, exploration agents).
- Why: The read-only mechanical verifiers were otherwise inheriting whatever expensive model drove the session. On a flat subscription this buys speed and rate-limit headroom rather than money; on metered billing it is direct spend. Either way there is no quality argument for running a docs-coverage check on the strongest model.
- Alternatives rejected (and why): All roles on the strongest model (maximum cost and rate-limit pressure for no measurable gain on mechanical checks); no agents at all (loses the independent fresh-context reviewer, which is the point of the verifier set).
- Note: concrete model names live only in each tool's config file, never in the skill or the lock — so a model name that ages never reaches a file that travels.
- Materialized: `.claude/agents/` (reviewers `claude-sonnet-5`, mechanical `claude-haiku-4-5`; Cursor reads this tree natively), `.gemini/agents/` (reviewers `gemini-2.5-pro`, mechanical `gemini-2.5-flash`). Codex and Windsurf have no subagent mechanism — the inline fallback runs on the session model, as designed.
- **Open gap — GitHub Copilot:** the `model:` frontmatter key exists in Copilot's custom-agent reference, but no source enumerates its accepted values, and the format is inconsistent across surfaces (VS Code documents display names such as `Claude Opus 4.5` / `GPT-5.2 (copilot)`; community examples use bare slugs; there is a known CLI/VS Code string-vs-array incompatibility, github/copilot-cli#2133). The key was therefore **omitted rather than guessed**: the four `.github/agents/*.agent.md` files each state that the binding falls back to the session model. Re-attempt when Copilot documents the accepted values.
- Supersedes: none

## D-017 — Repositioning: lead with the PHP + MCP + static + multilingual intersection; x402 leaves the marketing
- Date / phase: 2026-07-18 / Adoption step 6
- Decision: The product's headline message becomes **"the PHP CMS with MCP and static generation in the core — multilingual out of the box, on the hosting you already have"**. x402 is removed from the marketing message; **the x402 code stays in the product, untouched**. "AI-first CMS" is retired as the differentiating claim.
- Why (evidence, `docs/00-competitive-landscape.md`): (a) "AI-first CMS" is commoditised — WordPress core shipped the Abilities API in 6.9, Lovable is at ~$500M ARR, and Cloudflare's EmDash (MIT, self-hostable, MCP-native, Astro-based, shipped 2026-04-01) matches most of the differentiation list with 11.3k stars to Klytos's 10. (b) x402 shows zero demand across seven CMS repos, ~77% volume collapse and ~50% wash trading, and Cloudflare abandoned pay-per-crawl in July 2026 — EmDash shipping it drew 3 comments out of 504. (c) No PHP CMS has both MCP and static generation in core: Statamic needs Laravel and $349/site, Grav's MCP is a Node sidecar, WordPress's static story is plugin-only with WP2Static dead. (d) Multilingual is the highest-volume unmet defect cluster in the category (Tina has no i18n; Decap's issue open since 2020) and Klytos's 20 in-sync locales appear nowhere in its positioning.
- Time limit on this: the official PHP MCP SDK is now Symfony / PHP-Foundation maintained, so the empty intersection should be expected to fill within roughly twelve months.
- Alternatives rejected (and why): keeping x402 in the marketing (the evidence is not merely absent, it is negative — and it costs credibility on the pillars that are real); keeping "AI-first CMS" as the headline (out-marketed and out-resourced on that exact claim); dropping x402 from the code too (it costs nothing to keep, and the thesis may return).
- Consequences: `README.md`, the root `index.html` landing page and any future Phase 8 site follow this message. Audit D-05 (README's stale "160+ tools / 75+ hooks" vs the real 206 and 411) is fixed in the same work — on the extensibility axis the project undersells itself more than fivefold.
- Note recorded honestly: the biggest risk identified by the scan is **not** competition but distribution — 10 stars and a bus factor of 1, with three architecturally similar projects (LightCMS 23 stars, Seite 13, VoxelSite 4) documented as having been right and gone nowhere. Repositioning addresses visibility; it does not address the bus factor.
- Supersedes: none

## D-020 — MCP tool authorization deferred to Sprint 2, not folded into Sprint 1
- Date / phase: 2026-07-18 / Phase 5, Sprint 1 planning
- Decision: The newly found gap NEW-02 — `klytos_has_permission` appears **zero** times across all 34 files and 172 tools in `installer/core/mcp/tools/` — is fixed in a **dedicated Sprint 2**, not added to Sprint 1. Sprint 1 builds the `klytos_require_permission()` helper that Sprint 2 reuses.
- Why: Gating 172 tools needs its own tool→capability map, an enforcement point in `ToolRegistry`, and its own test set. Folding it into Sprint 1 would roughly double the sprint and delay the admin-side authorization fix that is already triaged and planned. A sprint that cannot close is worse than two that can.
- Stated plainly, not buried: **when Sprint 1 closes, the admin surface is gated and the product's primary interface is not.** MCP auth proves *who* the caller is, never *what* they may do, so any app-password holder currently has owner-level power over the CMS.
- Alternatives rejected (and why): adding it to Sprint 1 (no window where admin is gated and MCP is not — but Sprint 1 stops being closeable); a coarse blanket owner-gate in `ToolRegistry` now (closes the escalation fast, but over-restricts legitimate editor/viewer MCP use until the fine-grained map lands, and an over-restrictive gate tends to get reverted under pressure rather than refined).
- Supersedes: none. Extends the D-018 triage with a finding that did not exist when it was made.

## D-021 — `klytos_current_user()` fails closed, with a migration for the installed base
- Date / phase: 2026-07-18 / Phase 5, Sprint 1 planning
- Decision: The v1.x compatibility fallback in `klytos_current_user()` (`installer/core/helpers-global.php:390-397`), which returns a hardcoded `'role' => 'owner'` whenever `$auth->getUserId()` is empty or `UserManager` throws, is changed to return **null (deny)**. The existing `UserManager::migrateFromV1Config()` (`user-manager.php:646`) is wired into boot as an idempotent migration so live v1.x installs get a real owner record instead of being locked out.
- Why: Any authenticated session lacking `klytos_user_id` is currently promoted to owner silently. This defeats **every** gate Sprint 1 adds, which makes it a prerequisite rather than an addition. It was not in the adoption audit — it was found during the Sprint 1 kickoff re-validation, which is precisely what that step exists for.
- Alternatives rejected (and why): remove the fallback with no migration (safest against escalation, fastest to ship — but a v1.x install whose migration has not run locks out its owner, and this is a self-updating CMS with production installs, so that is a real support incident); keep it, narrow it and log it to measure real-world frequency (lowest breakage risk, but leaves the escalation open for the whole sprint while the sprint's entire purpose is closing it).
- Verification required (not optional): the upgrade path is tested **from the real previous version**, not only from a clean install — mandatory whenever `Installed base: yes`.
- Supersedes: none.

- Date / phase: 2026-07-18 / Phase 5, Sprint 1 planning
- Decision: A root `composer.json` is added with **`require-dev` only** (`phpunit/phpunit`, `squizlabs/php_codesniffer`). The runtime stays dependency-free. `composer.json`, `composer.lock` and `vendor/` are export-ignored so nothing ships. ## D-023 — Theme becomes an installable, validated package; design enters via an authoring skill
- Date / phase: 2026-07-18 / Phase 5 (scope change, designed only — not implemented)
- Decision: The frontend visual layer is redesigned around a **theme package**: a directory with a manifest (`klytos-theme.json`, ID = directory name, mirroring the immutable plugin contract) owning its templates, parts, CSS, self-hosted fonts and assets, plus style variations. Klytos stops shipping a look and instead guarantees a **contract** in three parts — placeholder vocabulary, an expanded frontend token system, and a landmark/accessibility contract — while fixing nothing about arrangement. A design produced by Claude Design (or any agent) enters through a new `klytos-theme-authoring` skill and is **refused at install time by a validator** if it violates the contract. Templates gain `extends` inheritance. The design brief becomes a machine-readable artifact stored with the theme. Full spec: `docs/theme-package-model.md`.
- Why: The starting premise (that Klytos over-restricts header/footer) is false and the code disproves it — `klytos_set_part` already accepts completely free HTML/CSS for any named part (`installer/core/mcp/tools/part-tools.php:88-89`). The real defect is that this freedom has **no contract**: the design brief is never persisted (prose in a chat transcript, `installer/core/guides/site-builder.md:85-166`), the frontend exposes only 14 CSS variables against the admin's ~118, base CSS is a 243-line heredoc inside PHP (`build-engine.php:1543`), distinctive design is deliberately steered into per-page `wp:html` blobs outside every system, and nothing is portable or versionable. Decisively, audit A-05 (HIGH) records **zero** `aria-`/`role=` attributes in the generated output: an unvalidated free-HTML part system makes that permanently unfixable, and under the EAA the exposure lands on Klytos's users (D-007). A validated contract is the only mechanism that fixes accessibility at the system level rather than once per site.
- Alternatives rejected (and why): extending the current record with more knobs (leaves base CSS in PHP and the design as a `custom_css` blob — treats the symptom); a freeform HTML/CSS importer as the canonical path (no contract, so unpredictable results, unmaintainable output and no accessibility guarantee — it may exist later as an assisted converter that still emits a package through the same validator).
- Consequences: closes the shipped model drift — `klytos_set_part` vs the superseded global-blocks model still taught by the `klytos-custom-templates` skill, which no shipped skill reconciles today. The structural heuristics in `build-engine.php:553-660` (raw `<header` string matching + top-bar auto-injection) are replaced by manifest-declared structure. A default package generated from today's `getBaseCss()` + the 26 scalars keeps every production install rendering byte-identically (installed base is real).
- Relation to D-009: does **not** supersede it. D-009 records that the pre-Keel UI has no design contract and that the current look is the baseline; that remains true for the admin. D-020 establishes, for the frontend and on the new model, the contract D-009 recorded as absent.
- Sequencing (explicit user decision): **planned now, implemented after Phase 5 Sprint 1** (S-01…S-09 + T-01, D-018). The authorization axis does not wait for a theme redesign. As a genuine redesign it then runs through Keel Phases 3–4 — the first time this project does — which is also the review trigger for the deferred `design-fidelity-auditor`.
- Supersedes: none

## D-024 — The design agent connects over MCP as an authoring loop, package-scoped and preview-only
- Date / phase: 2026-07-18 / Phase 5 (scope change, designed only — not implemented; extends D-023)
- Decision: Klytos exposes a dedicated **design authoring surface** over its existing MCP server so an external design agent (Claude Design or any other MCP-capable agent) can connect to a site and work against it. The surface is deliberately shaped as a **read → validate → preview → iterate loop whose unit of exchange is the theme PACKAGE, never an individual mutation**: the agent reads the contract and a description of the site, submits a complete package, receives concrete validation errors or a rendered preview, and iterates. It works **only against a preview target**; activating a theme on the published site is a separate human action. Individual write tools (`klytos_set_part`, `set_colors`, `custom_css`) are NOT part of this surface.
- Why: The obvious shape — letting the design agent push the design live, mutation by mutation — was rejected because it reproduces the exact defect D-023 diagnoses: imperative, runtime, unvalidated, site-bound design that is not portable, not versionable and not auditable. It would also be no new capability, since the MCP server already exposes those write tools today. What the design agent genuinely lacks is (a) the ability to READ the site and the contract it must satisfy — today it designs blind, which is why the brief degenerates into prose — and (b) a feedback loop with real rendered output. MCP is the right transport for both, and package-scoping keeps D-023's invariant intact: the package is the artifact, the validator is the gate.
- Security rationale (this is the decisive constraint, not a footnote): `klytos_set_part` accepts a `js` parameter that is emitted as a `<script>` tag on **every page**, and stores `html` without passing it through `kses` (`installer/core/mcp/tools/part-tools.php:88-99`, `installer/core/part-manager.php:84-85`). A live-write design surface therefore hands an external agent global stored-XSS on a production site, on the very axis (authorization) the project already records as its weakest — D-018, S-01…S-09. Preview-only + package-scoped + a dedicated `theme.*` capability + separate human activation bounds the blast radius. Applies both security profiles per D-003; the stricter wins.
- Alternatives rejected (and why): **live direct write** (immediate and superficially simpler, but recreates the diagnosed defect and opens the JS-injection path above); **read-only** (safest and simplest, package delivered out of band as a file — but it drops the render-feedback loop, which is half the value and the reason the current prose-brief model fails).

## D-030 — The integration tier isolates by snapshot/restore of the whole playground, and fails loudly where it cannot
- Date / phase: 2026-07-19 / Phase 5, Sprint 1 — deferred item resolved before slice 3
- Decision: The integration tier snapshots `installer/config/` and `installer/data/` before every test and restores them afterwards (`tests/PlaygroundState.php`, used by `IntegrationTestCase`). Isolation is **ON by default for every test in the tier**, opt-out only with a recorded reason. Where a file-level restore provably cannot reach — in-memory caches held by the booted App singleton — the primitive does **not** pretend to cover it: `assertConfigNotMutated()` fails the test with instructions instead.
- Why: The slice-1 `code-reviewer` pass raised that the tier shares the App singleton *and* the real on-disk playground with no rollback. Slice 1's tests were read-only, so nothing broke; slices 3-5 assert refusals on state-changing surfaces, and they would have become order-dependent within a run while permanently mutating the playground across runs.

That record belongs to the seed, not to the test, so a create-and-destroy fixture cannot express it. The cost objection does not apply either — a seeded playground is **31 files / ~124K**, so a full copy per test is microseconds; measured suite time went from 0.049s to 0.187s for 14 tests.
- Verified before deciding, not assumed (subagent scan of `installer/core/`): the storage layer memoizes **nothing** — `FileStorage::read/list/count/exists`, `UserManager` and `SiteConfig` touch the filesystem on every call — which is exactly why a file-level restore is sound for the users, pages and site-config records slices 3-5 assert against. Four caches survive a restore and are named in the trait's docblock with file:line: `App::$config` (app.php:217, read once at boot, **no invalidation path at all**), `EncryptionLevelTrait::$cachedEncryptionLevel` (held by the live storage object — the sharpest, because a stale value corrupts writes rather than reading stale data), `OptionsManager::$cache` plus its static `$sensitivityRegistry`, and `AiKeyManager::$cache`.
- Proven, not asserted: `tests/Integration/PlaygroundIsolationTest.php` deletes a seeded user, confirms the mutation took effect and the on-disk fingerprint changed, then asserts the next test sees the untouched playground — record restored **and** byte-for-byte fingerprint match, including permission bits. Demonstrated to FAIL with isolation disabled (`testBPlaygroundIsRestoredForTheNextTest` → "the playground was NOT rolled back") before being trusted; the proof run really did delete the user, and the playground was reseeded afterwards.
- Alternatives rejected (and why): **per-test fixtures** (cheapest and needs no primitive, but cannot express slice 3's migration test, as above); **adding `App::reset()` to the product** (would close the `App::$config` gap properly — but it is core surgery on a singleton in a sprint whose subject is authorization, exactly the tangling D-025 refused for `phpcbf` and D-026 refused for `Hooks::doAction()`); **reflection on the private `$instance`/`$config`** (no product change, but silently couples the harness to private internals that may be renamed with no compiler to catch it); **opt-in isolation per test** (cheaper, but which tests mutate is precisely what cannot be known in advance — a helper three calls deep writing a rate-limit counter is still a mutation).
- Ordering detail that is load-bearing: the snapshot is taken **before** `App::boot()`, because boot itself writes (Step 10b's migration, the action scheduler). Restore runs before the config assertion, so the playground is left correct even when the assertion fails.
- Trigger for revisiting: the first test that genuinely needs to mutate core config, options, the encryption level or AI keys. At that point either run it with `#[RunInSeparateProcess]` or reopen the `App::reset()` question as its own change — not in passing.
- Supersedes: none. Resolves the "Storage isolation for the integration tier" deferred item (PROGRESS.md) and sprint-1 risk 4.

## D-032 — Authorization is enforced centrally, keyed by executed file, and denies by default
- Date / phase: 2026-07-19 / Phase 5, Sprint 1 slice 4
- Decision: The admin authorization gate moves from 66 individually-remembered per-file checks to a single enforcement point. `installer/core/admin-gate.php` holds a **gate map** (65 admin surfaces → required capability), and `admin/bootstrap.php` — which all 66 admin files require — calls `klytos_enforce_admin_gate()` once, after its auth guard. A surface **absent** from the map is REFUSED. `klytos_require_permission()` and `klytos_deny()` are added to `helpers-global.php` as the reusable enforcing counterparts to `klytos_has_permission()`, and Sprint 2's MCP gating consumes the same pair.
- Why this shape and not "add 51 missing calls": the audit's own remediation note asked for a call at the top of every file, and that has the identical failure mode one file later — a new admin page defaults to OPEN. Default-deny inverts it: a new page is refused until someone maps it deliberately, and `scripts/keel-verify` fails the build when a file under `admin/` has no entry. The 51 missing gates were never a discipline problem; they were a design in which forgetting was possible.
- Verified before relying on it, not assumed: **all 66 admin files require `admin/bootstrap.php`** (checked mechanically, zero exceptions), which is what makes one call sufficient. `plugin-page.php` was already gated correctly via `Router::handleDynamicRoute()`'s shape (`core/router.php:438-447`); that shape was **promoted** into `klytos_deny()` rather than a second one being invented.
- Keyed by **path relative to `admin/`**, not basename: six filenames (`ai-chat.php`, `logs.php`, `plugins.php`, `tasks.php`, `terminal.php`, `translations.php`) exist in BOTH `admin/` and `admin/api/`, and a basename key would silently collapse six pairs of unrelated surfaces onto one capability.
- Resolved from **`SCRIPT_FILENAME`**, not `SCRIPT_NAME`: the latter is URL-derived and therefore caller-influenced. A path that does not resolve inside `admin/` yields no key and is denied — traversal resolves to its real location and fails the prefix test.
- `bootstrap.php` is deliberately **unmapped**, so a direct request for it hits default-deny. It hosts the gate; it is not a surface the gate protects. `keel-verify` asserts it stays unmapped.
- **Refusal shape is part of the contract, not cosmetics.** `klytos_deny()` answers JSON for `api`/`mcp`, stderr+exit(1) for `cli`, and a self-contained escaped HTML document for pages. The page document carries no admin chrome on purpose: the gate runs before a page has built its own context, and a gate that can fatal while rendering a refusal is not a gate — the same reasoning L-006 recorded for the boot-time logger. Four pages (`logs`, `system-options`, `translations`, `terminal`) previously *redirected to the dashboard* on denial, which a caller cannot distinguish from "moved"; they now refuse with 403.
- **Five capabilities added** to the one matrix (S-04 is preserved — `UserManager::hasPermission()` remains the single decision point): `profile.edit`, `security.self`, `ui.preferences` (all four roles — the self-service tier, which nothing in the pre-existing 22 expressed, since `users.manage` is owner-only and would have locked every non-owner out of their own password), `setup.run` (owner-only) and `ai.use` (owner+admin, see D-035). Expressed as capabilities rather than an "authenticated, no capability" marker so that ONE mechanism decides authorization, filterable through `auth.capabilities` like every other row. Recorded upgrade note: a role added later does NOT inherit these and is denied its own profile until the matrix says so — the correct failure direction, and a real consequence.
- **Page-level is a floor, not a ceiling.** Pages mixing tiers map at the level needed to SEE them and re-gate privileged branches inline (`index.php` → `site.configure` on the indexing toggle; `pages.php` → `pages.delete` on trash/purge; `tasks.php` → `tasks.manage`; `security.php` → `site.configure` on the encryption branch). Mapping those pages at the higher tier instead would have locked editors and viewers out of the page list entirely.
- Extension points, with the risk stated rather than buried: `admin.gate_map` (filter) lets a plugin gate its own files and CAN weaken a shipped gate — exactly as the pre-existing `auth.capabilities` filter can; both are plugin-trust boundaries and plugins already run as first-party code here. What it cannot do is open a hole by omission, since removing an entry denies. `auth.access_denied` (action) is the audit hook and deliberately **cannot reverse the decision** — a filter that could turn a denial into a grant would put authorization back in third-party hands, which is the failure S-07 exists to close.
- Alternatives rejected (and why): **per-file `klytos_require_permission()` calls in all 66** (what the audit note suggested, and closest to the existing code — but it preserves the exact defect, since file 67 can still forget); **gating in the web server / `.htaccess`** (no capability awareness, and the product supports storage backends and a renameable install directory); **a route table in front of the admin** (cleanest long-term, but it is a rewrite of the admin entry model in a security sprint, and the theme-package sprint D-023 will revisit routing anyway).
- Supersedes: none. Closes audit **S-07**, and closes the *access* half of S-01, S-02, S-03, S-05 and S-06 — each of which slice 5 still proves individually with its own named test, and S-12's CSRF/state-changing-GET half remains slice 5's.

## D-039 — The config-mutation guard was inert; it now compares decrypted content, minus volatile keys
- Date / phase: 2026-07-19 / Phase 5, Sprint 1 slice 5
- Decision: `PlaygroundState::assertConfigNotMutated()` — introduced by D-030 as "the honest half" of the isolation primitive — **could not fail**, and is repaired. It now captures the config file's bytes **before** `restorePlayground()` overwrites them, and compares **decrypted content with `scheduler_last_run` removed** rather than hashing the raw file.
- What was wrong, and it was wrong from the day it shipped: the method runs after `restorePlayground()`. That ordering is correct and deliberate (D-030: the playground must be left clean even when the assertion fails) — but the method then re-read the file *live*, which is the file the restore had just put back. Every comparison was the snapshot against itself. The guard had been carrying the credibility of the whole integration tier since slice 3 and was checking nothing.
- Proven, not reasoned: a probe test wrote a marker key into core config and **passed green**. After the repair the same probe **failed** with the intended message. Both directions were observed before anything relied on it — the discipline slice 2 applied to the manifest drift guard and slice 3 to the migration test.
- Why the comparison moved from a file hash to decrypted content, which is a second defect the repair had to absorb: (a) the file is **encrypted**, so rewriting byte-identical content still produces different ciphertext — a byte comparison cannot distinguish "changed" from "written again"; (b) `ActionScheduler::setConfigValue()` (`action-scheduler.php:398`) writes `scheduler_last_run` whenever due actions are processed, and `App::boot()` triggers that on **every** request. The HTTP tests boot a real server per request, so core config is rewritten from a separate process as a matter of course. The repaired byte-hash guard failed **ten healthy tests** immediately — a true observation about the file and a false one about the tests. A guard that cannot tell a background heartbeat from a test's own write gets switched off within a week, and then it is inert a second time.
- Undecryptable input fails **towards** noticing: if the ciphertext cannot be decrypted (a test changed the encryption level, a truncated write) the raw bytes are compared instead, so a difference nobody can read still counts as a difference. Treating "I cannot read this" as "nothing changed" is the failure mode being repaired, not a fallback to it.
- Regression cover, permanent rather than a throwaway probe: `tests/Integration/PlaygroundGuardTest.php` asserts both halves — a real config mutation trips the guard, and a `scheduler_last_run`-only change does not. It opts out of automatic isolation with a recorded reason (it IS the test of the primitive, so it cannot also be a client of it) and drives snapshot/restore by hand.
- Alternatives rejected (and why): **move the assertion before the restore** (the obvious repair, and it makes the live re-read correct — but it reverses D-030's safety ordering, so a failing assertion would leave the mutated playground in place for every following test, trading a silent false green for a loud cascade); **exempt the HTTP test classes from the guard** (fastest way to green, but it removes the check from exactly the tests that touch the most surfaces); **keep the byte hash and accept ten failures** (honest but unusable — the heartbeat is not a defect and a permanently red suite teaches people to ignore it).
- Supersedes: none. Repairs the mechanism D-030 specified; D-030's reasoning stands unchanged, its implementation did not.

## D-041 — SSRF is refused by one class applied at the influenced call sites, and redirects are walked by hand
- Date / phase: 2026-07-19 / Phase 5, Sprint 1 slice 6
- Decision: `Klytos\Core\SafeHttp` (`installer/core/safe-http.php`) becomes the single implementation of "may this URL be fetched", **promoted** from `KlytosImporter\ImportValidator::validateUrl()` rather than written fresh. It is applied at the call sites whose URL an untrusted party influences — `admin/api/oembed.php` (S-08), `core/webhook-manager.php` (both `create()` and `sendHttpPost()`), `core/integrity-checker.php::registerDeveloperKey()` — and `ImportValidator` now **delegates** to it. `klytos_http_get()` / `klytos_http_post()` are deliberately left unchanged. Reached via `klytos_safe_http()`.
- Why promotion and not a new implementation: the check already existed and worked; what it lacked was reach. Writing a second one would have created exactly the drift L-004 records — two surfaces describing the same rule, free to diverge, with the forgotten copy rotting. This is the same move slice 4 made when it promoted the denial shape out of `router.php:438-447` instead of inventing a second one.
- Why the class is a FETCHER and not just a validator, which is the load-bearing part: pre-flight validation is necessary and **not sufficient**. A public host that passes the check can answer `302 Location: http://169.254.169.254/`, and both cURL's `CURLOPT_FOLLOWLOCATION` and PHP's http wrapper follow it without consulting anyone. **Measured, not assumed:** `CURLOPT_REDIR_PROTOCOLS` is set **nowhere** in this repository, the four `stream_context_create` fetch sites set no `max_redirects` and therefore inherit PHP's default of **20**, and only one call site in the entire product (`PageFetcher::fetch()`) re-validated after a redirect at all — and that one checks only the FINAL url, after the body has already been fetched. So a validated call site was still one attacker-controlled redirect away from the metadata endpoint. SafeHttp turns the transport's redirect handling off and walks the chain itself, re-validating every hop, with method/body following RFC 9110 §15.4 so callers keep the behaviour they had.
- The finding was WIDER than the audit recorded, and this is the part worth carrying forward: S-08 described one arbitrary fetch (`discoverOembed( $url )`). Reading the file for the fix found a **second** one — the endpoint *discovered inside* the fetched page (`<link type="application/json+oembed" href="...">`) is equally attacker-controlled, and unlike the page fetch **its response is echoed back to the caller** (whole on success, first 500 bytes on a JSON parse failure). That is a full read-SSRF primitive, and validating only the caller-supplied URL would have left it open. Every fetch in the file now goes through one function for that reason.
- Refusals answer as the generic failure, never as an oracle: `oembed.php` returns the same `400 Invalid URL` for a refused private address as for a malformed one. A distinct reply per reason would turn an authenticated editor into an internal-network scanner, one address per request. The specific reason goes to `error_log()` and the `http.safe.blocked` action.
- Why `klytos_http_get()` was NOT made safe by default: it would refuse any plugin legitimately calling a LAN or localhost service — a breaking change for third parties, which in this project needs its own decision and release note (the D-034 precedent), not a quiet inclusion in a security slice. Plugin authors fetching untrusted URLs call `klytos_safe_http()`; the reference doc says so in those words.
- Extension points, with the risk stated rather than buried: `http.safe.allowed_schemes` and `http.safe.max_redirects` (filters) **can** weaken a shipped control, exactly as `admin.gate_map` can (D-032) — both are plugin-trust boundaries and plugins already run as first-party code here. What neither can do is open a hole by omission, since the default is an allow-list. `http.safe.blocked` is an **action, not a filter**: a listener able to turn a refusal into a grant would put SSRF policy back in third-party hands, which is the same reasoning that shaped `auth.access_denied`.
- Fixed in-path, per D-031's narrowing: `HttpClient::requestWithStream()` accepted `follow_redirects` at `request()` and then **dropped it**, hardcoding `follow_location => 1`. A caller that switched redirects off got them anyway whenever `ext-curl` was absent — which would have handed back the exact SSRF SafeHttp exists to prevent, on precisely the hosts least likely to notice. The slice was already changing this transport; leaving it would have shipped a control with a documented bypass.
- Second known limit, found by reading the transport rather than by testing it, and documented rather than closed: `HttpClient::request()` applies the `http.before_request` filter to the method, URL and options at `http-client.php:91` — **after** `SafeHttp` has validated. A plugin listening there can substitute a private address post-check. This is the same plugin-trust boundary as `admin.gate_map` (D-032), so it is consistent with how this project already treats plugin code, but it is named explicitly in `docs/reference/safe-http.md` because — unlike `http.safe.allowed_schemes` — it is not a hook anyone would expect to be a security surface. Moving the validation below the filter was considered and rejected for this slice: it would mean `SafeHttp` reaching past `HttpClient`'s public API into its transport methods, which trades a documented plugin-trust issue for a structural coupling, and the filter predates this slice.
- Known limit, recorded as **NEW-15** and stated in the reference doc rather than implied away: DNS rebinding survives. The host is resolved to validate and resolved again to connect. Closing it means pinning the validated address (`CURLOPT_RESOLVE`), which changes `HttpClient`'s contract for every caller and needs a resolver the test can control. **Slice 6 raises the cost of SSRF substantially; it does not make it impossible**, and saying otherwise would be the L-002 defect verbatim.
- Alternatives rejected (and why): **validate at the oEmbed call site only** (closes the named finding with the smallest diff — but leaves the AI-reachable webhook URL behind `FILTER_VALIDATE_URL`, leaves two copies of the check, and leaves the discovered-endpoint fetch open); **make `HttpClient` refuse private addresses for everyone** (widest coverage, and the right long-term end state — but it is a breaking change for third-party plugins landing inside a security slice, which is the tangling D-025/D-026/D-029/D-031 have each refused in turn); **keep `CURLOPT_FOLLOWLOCATION` and re-validate only the final URL** (what `PageFetcher` does today — cheapest, and unsound: the body has already been fetched from the internal host by the time the check runs, and intermediate hops are never seen at all).
- **Amended after the slice's own review cycle, before commit.** Both review subagents ran on the diff and between them, plus one finding neither produced, the slice grew materially. Recorded here rather than silently folded in, because the shape of what they caught is the transferable part:
  - **A live bypass in the new class, found by testing rather than by either reviewer.** `filter_var`'s reserved-range flags do not understand IPv4-mapped IPv6, so `http://[::ffff:127.0.0.1]/` was ALLOWED and verified to fetch loopback for real (HTTP 200, body returned). Every private address has such a spelling. `isReservedAddress()` now normalizes IPv4-mapped and IPv4-compatible IPv6 to dotted-quad on the packed bytes before classifying. The `security-auditor` raised the case and reasoned past it — "very likely already handled correctly" — which is why **L-013** exists: a reviewer's reassurance is a hypothesis exactly like a reviewer's accusation.
  - **A dual-stack gap:** `gethostbynamel()` reads A records only while the transport is dual-stack, so a public A plus a private AAAA passed. `resolveHost()` now reads AAAA too and every returned address must pass. No rebinding trick needed for this one — two DNS records.
  - **The same file had a second, unfixed untrusted fetch.** `integrity-checker.php::httpGet()` takes its URL from `resolvePluginManifestUrl()`, i.e. an external plugin's `Integrity URL` header — the *same* untrusted plugin file, parsed by the *same* parser, as the `Integrity Key URL` this decision originally fixed. It had raw cURL, `FOLLOWLOCATION`, and no address check at all. Fixing one of two identical paths in one file is precisely the failure this class exists to end, and the first draft of this decision did exactly that.
  - **The importer's three fetchers were converted after all**, reversing this decision's original scope. `PageFetcher::fetch()`, `PageFetcher::fetchRobotsTxt()`, `MediaDownloader::downloadFile()` and `SitemapParser::fetchXml()` now call `fetch()` rather than validating through `ImportValidator` and then issuing their own `CURLOPT_FOLLOWLOCATION` request. The original draft left them, and both reviewers called that blocking with the same argument: the audit's own S-08 text names them, and this decision's "alternatives rejected" list cites `PageFetcher` **by name** as the unsound pattern while shipping it unchanged. `MediaDownloader` was the worst of them — it never re-checked the destination even once, so a redirect into the internal network wrote that response to disk as a servable "media asset". `docs/reference/safe-http.md` had also claimed these paths were covered, which was the L-002 defect in a document written in the same slice that warns about it.
  - **A new oracle was introduced and removed.** `WebhookManager::create()` initially threw a distinct message for a blocked address versus a malformed URL — reachable from the MCP tool `klytos_create_webhook`, which per NEW-02/D-020 has **no permission check** until Sprint 2, and echoed into the page by `admin/webhooks.php`. That is the scanner this slice deliberately avoided building in `oembed.php`, built in the same slice, three files away. Both messages are now identical.
  - Smaller, all confirmed against source before acting: `update()` gained the same check as `create()` (no caller today — which is exactly why); `absolutize()` now handles a query-only `Location` per RFC 3986 §5.3 and normalizes dot segments; the `http.safe.redirect` docblock no longer claims the hop was followed; and `IntegrationTestCase::tearDown()` runs the hook check **before** the config check, because a throwing config assertion would otherwise stop the hook check from ever running — L-010's masking shape one level removed.
- Supersedes: none. Closes audit **S-08**; opens **NEW-15**.

## D-042 — The integration tier records a hook baseline and fails a test that leaks one
- Date / phase: 2026-07-19 / Phase 5, Sprint 1 slice 6
- Decision: `IntegrationTestCase` captures `Hooks::getRegisteredHooks()` after `App::boot()` and asserts in `tearDown()` that the test handed it back unchanged. Throwaway listeners are registered with new `addTemporaryFilter()` / `addTemporaryAction()` helpers, which remove them by **callback identity**; a test using the raw `klytos_add_filter()` / `klytos_add_action()` and leaving a listener behind now FAILS with an explicit message.
- What was wrong: `UnitTestCase` calls `Hooks::reset()` before and after every test. The integration tier called it **never**. `Hooks` is static and `App::boot()` runs once per process, so any listener a test registered persisted for every test that ran afterwards in the same process.
- Why nobody had noticed, which is the transferable part: **no integration test had ever registered a hook.** The tier had been in use since slice 1 and the gap was invisible because nothing exercised it. Slice 6 is the first — its `http.safe.allowed_schemes` test permits `ftp://`, and that filter was silently permitting `ftp://` for every test that followed it. Caught by reading the tier's own refusal logs and noticing a later test reported `too_many_redirects` where `private_or_reserved_address` was expected: the *reason* was wrong, and the reason is exactly what the slice's tests assert on for this purpose.
- Nothing was passing for the wrong reason **yet**, and that is stated precisely rather than inflated: the affected assertions still held. But the next security test to register a weakening filter would have leaked it into everything downstream, and it would have looked exactly like a green suite — which is L-010's failure mode, one slice after L-010 was written.
- Why a baseline and not `Hooks::reset()`: a blanket reset would strip the core and plugin hooks `App::boot()` registered, for every test after the first, leaving the application quietly half-wired. The baseline is taken *after* boot, so it means "the application's own hooks" rather than "no hooks".

- Supersedes: none. Extends the isolation contract D-030 established for storage to cover hook state, which D-030 did not consider.

## D-044 — Security headers get ONE enforcement point, HSTS is HTTPS-only and subdomain-free, and the CSP fails closed
- Date / phase: 2026-07-20 / Phase 5, Sprint 1 slice 8 (HSTS policy and the page-editor scope question decided by the user)
- Decision: `Auth::sendSecurityHeaders()` is called **once**, from `installer/admin/bootstrap.php`, for every admin surface — the S-07 answer applied to headers. It gains `Strict-Transport-Security: max-age=31536000`, sent **only over TLS**, **without** `includeSubDomains`, filterable through `security.hsts`. Its CSP now **fails closed**: a caller supplying no nonce gets `script-src 'self'`, not the old `'self' 'unsafe-inline'`. The policy computation is split into a pure `Auth::buildSecurityHeaders()` so it can be tested at all. `Helpers::isHttps()` becomes the single HTTPS check, replacing four duplicated expressions.
- **Why one enforcement point rather than 25 calls** — this is NEW-14 and it is the S-07 shape exactly: the function had six call sites repo-wide and none was an admin API endpoint. Adding a call to each file has the identical failure mode one file later. Every admin file requires `admin/bootstrap.php` (verified mechanically this slice, not taken from slice 4's record: 73 PHP files under `admin/`, of which 9 are templates/partials/includes that are *included* rather than requested, leaving 64 entry points — the same 64 `scripts/keel-verify` counts).
- **The audit's own numbers were stale and its framing was wrong on two pages.** NEW-14 says "all 24 files in `installer/admin/api/`"; there are **23** — slice 7 deleted `comment-submit.php` (D-043). - **PLACEMENT IS THE LOAD-BEARING PART, and it is bounded on both sides.** Slice 7 established that a check placed after `App::boot()` is a cost an anonymous caller pays, and that a cheap branch before a limiter bypasses it; headers have the same shape, because *a header set after output has begun is not set at all*. The call sits immediately after the boot try/catch:
  - It cannot go **later**: everything below it in bootstrap emits or exits — the pending-rename redirect, the auth guard's 401 JSON and its 302, `klytos_deny()`'s 403 document, the setup-wizard redirect. All four are now covered, verified on real responses (the 401 and the 403 both carry `nosniff` on the wire).

This is L-006's rule applied before writing the line rather than after debugging it.

- **Why HSTS is HTTPS-only and carries no `includeSubDomains`** (user decision, chosen over the stronger variant): a browser caches the directive for the full `max-age` and honours it after the header stops being sent, so it is close to irreversible for an installed base. `includeSubDomains` would force HTTPS onto every sibling subdomain of the install's host — subdomains that belong to the operator, not to Klytos, and that may legitimately serve plain HTTP. Klytos is self-hosted software; opting somebody else's infrastructure into a year-long, hard-to-undo directive by default is not ours to do. Operators who want preload or subdomains widen it through `security.hsts`. Sending it over cleartext was rejected as well: browsers ignore it there, so it would be a claim the transport cannot back.
- **Why the CSP fail-open mattered more than it looked, and this is the finding of the slice.** The old fallback meant a caller that forgot a nonce silently received the weakest policy in the product, with nothing to signal it. That is bad on its own. What made it load-bearing here is that **`login.php` had no CSP at all** and carries an inline `<script>` — the 2FA method switcher. Giving every surface a CSP therefore *would have broken two-factor login* had the fallback stayed weak enough to hide it, or had the block not been nonced. A security fix that breaks authentication is worse than the gap it closes; nonce-ing `login.php` is in scope **by necessity**, the same shape as NEW-16 in slice 7.

This is not a lapse: `Router::dispatch()` `readfile()`s **pre-generated static HTML** (`router.php:303-326`), and the build engine writes inline `<script>` into it — the GDPR consent banner's `ConsentManager.init(...)` (`build-engine.php:881`) and a page's `custom_js` (`build-engine.php:444`). **A file generated once at build time cannot carry a per-request nonce.** Verified before deciding: failing closed there would have silently disabled the consent banner on every generated page of every site. Writing the policy out as a literal makes the weakening visible in a diff, which is precisely what the implicit fallback did not do. Recorded as **NEW-23**; the real fix belongs to the theme-package sprint (D-023), which owns generated output.
- **`style-src` keeps `'unsafe-inline'` deliberately, and a test asserts that weakness on purpose.** S-10 is explicitly out of scope (349 inline `style=` attributes across 40 files; an attribute cannot take a nonce). The trap that made this worth pinning: per CSP Level 3, adding a **nonce source** to `style-src` makes browsers **ignore** `'unsafe-inline'` — so "tidying" the policy by nonce-ing styles the way scripts are nonced would break the admin's rendering everywhere at once. The **10** `<style>` elements in `installer/admin/` now all carry nonce **attributes** that do nothing yet and are ready for the slice that removes `'unsafe-inline'` (4 already had them; 6 were added here). **The audit's "12" is wrong and is corrected in the same change**: it counted two `<style>` occurrences that are embedded inside `srcdoc` attributes (`blocks.php:82`, `block-data.php:172`), which build an iframe document as an escaped string and therefore cannot carry a nonce at all. Counting them made the S-10 estimate look larger than it is and would have sent the next slice hunting for two blocks that do not exist. `testStyleSrcStillAllowsInlineWhileS10IsOpen` exists so that removal is a deliberate act, not a side effect.
- **A false pass was caught in the slice's own test infrastructure, which is L-010 arriving for the third time.** The first unit tests drove `sendSecurityHeaders()` and read `headers_list()`. Under the **CLI SAPI `header()` is a no-op and `headers_list()` returns an empty array**, so all three "the header is ABSENT" assertions passed against an empty string — and would have passed against code that set no headers at all. They were caught only because the *presence* assertions in the same file failed loudly for the same underlying reason. The repair is the `buildSecurityHeaders()` split: the unit tier now asserts the **policy** and the integration tier asserts it **reaches the wire**. A second false pass was caught by probe in the integration tier: an assertion searching the whole response body for the nonce still passed with the nonce stripped from the `<script>` tag, because `login.php`'s `<style>` block carries one too.
- Alternatives rejected (and why): **add `sendSecurityHeaders()` to all 25 surfaces** (matches the audit's implicit shape and is closest to the existing code — but surface 26 forgets, which is the defect S-07 exists to end); **send the headers from `.htaccess`/the web server** (no nonce awareness at all, and the product supports a renameable install directory and multiple storage backends); **`includeSubDomains` now** (stronger, and rejected above on installed-base grounds); **fail the CSP closed everywhere including `index.php`** (uniform and simple, and it silently breaks the consent banner on every generated site — rejected on verified evidence, not on caution).

## D-046 — MCP tool authorization is one enforcement point in `ToolRegistry::call()`, default-deny, with a per-request actor and a JSON-RPC refusal
- Date / phase: 2026-07-22 / Phase 5, Sprint 2 planning (the four underlying user decisions were taken 2026-07-21; the plan was approved 2026-07-22)
- Decision: NEW-02 is closed by a **single** enforcement point inside `ToolRegistry::call()` (`installer/core/mcp/tool-registry.php:159`), placed **above** the `mcp.handle_tool` filter (`:164`) so it covers plugin-handled tools as well as the built-in table. It denies by default — no actor, an unmapped tool, or a role that lacks the tool's capability all throw a typed `Klytos\Core\MCP\PermissionDeniedException`. The decision remains `UserManager::hasPermission()` (S-04, the ONE matrix); the gate asks it, it does not add a second one. The MCP credential's identity is carried per request on the `ToolRegistry` instance via a **new** `setActor( int|string $userId, string $role )` — the registry is already built fresh per request (`server.php:40`), so no global is introduced — set by `server.php` after authentication and by `chat-engine` from the session; `call()` and `listTools()` read the actor.
- **Why this shape and not the recorded one-liner:** D-020 / `authorization.md:217` said "reuse `klytos_require_permission()` at the ToolRegistry enforcement point". Dropped in as-is it would **deny 100% of MCP traffic**, because `klytos_require_permission()` resolves identity from the session and there is no session on the MCP path — `Auth::startSession()` runs only in the admin path (`auth.php:62`, from `admin/bootstrap.php:216` and the OAuth consent view), while `Router::handleMcp()` (`router.php:123-147`) → `mcp/server.php` never starts one, so `klytos_current_user()` returns null (`helpers-global.php:370-376`). Identity has to be built from the credential first (D-047), and the gate consumes that actor rather than the ambient session. Verified against source this session by two Explore agents.
- **Why above the plugin filter, verified not assumed:** `mcp.handle_tool` (`:164`) can satisfy a call and `return` (`:165-169`) before the registered-tool table at `:171`. A gate below it would leave every plugin-handled tool ungated — the same by-omission failure S-07 exists to close. `call()` is reached by exactly two callers repo-wide (`server.php:225`, `chat-engine.php:309`) and no third, so one gate covers the whole surface.
- **Refusal shape is part of the contract, and it is DICTATED by the transport, not chosen.** The MCP server speaks JSON-RPC error objects everywhere (`JsonRpc::error( int $code, string $message, mixed $data = null, string|int|null $id = null ): array`, `json-rpc.php:84-100`). So `klytos_deny('mcp')` is **not** reused — it is absent from the MCP path today (0 matches) and its `{error,code}` body is not a JSON-RPC error object. Each transport catches `PermissionDeniedException`: `server.php::handleToolsCall()` emits `http_response_code(403); Helpers::jsonResponse( JsonRpc::error( -32000, …, $id ), 403 )`, mirroring the existing 401 auth-failure block (`server.php:103-108`) and keeping the id correlation; `chat-engine` returns a model-visible tool error. **This explicit-status step is mandatory, not cosmetic:** the normal dispatch emits via `Helpers::jsonResponse( $response )` with no status arg, which defaults to **HTTP 200** (`server.php:177`), so a denial merely *returned* as an error array would ship as 200. Verified this session.
- **`tools/list` is filtered by the actor's capabilities via the same map, and `tools/call` gates independently.** The list filter runs in `listTools()` after the `mcp.tools_list` plugin filter (`tool-registry.php:103`) and before the return (`:113`), so plugin-added tools are filtered too; but `call()` never trusts what `tools/list` returned — a caller naming a tool the list omitted is gated on its own. Hiding is not access control; the gate is.
- Alternatives rejected (and why): **reuse `klytos_require_permission()` verbatim at the choke point** (the recorded plan — denies all MCP traffic, see above); **a coarse owner-only gate in `ToolRegistry` now** (closes the escalation fast but over-restricts legitimate editor/viewer MCP use and tends to be reverted under pressure — the D-020 argument); **gate below the `mcp.handle_tool` filter** (simpler diff, leaves all plugin tools ungated); **reuse `klytos_deny('mcp')`** (its body is not a JSON-RPC error object, so an MCP client cannot parse it as one).
- Supersedes: none. Implements **D-020**; consumes D-047's actor and D-048's map. Closes the forward reference at `authorization.md:217-221` (done in slice 4).
- **Implemented in slice 2, with three mechanism notes (outcome unchanged):** (1) `setActor()`'s signature is `setActor( int|string|null $userId, ?string $role )`, not the literal `int|string $userId, string $role` this decision sketched — a **bearer token has a null user_id** (D-047), and it is the sprint's own end-to-end proof credential, so a non-nullable user id could not represent it; a deleted user record (NEW-08) yields a null role. Both nullable cases deny, exactly the fail-closed intent. (2) The gate's decision lives in ONE private `denialReason()` that both `call()` (throws on a non-null reason) and `listTools()` (drops tools with a non-null reason) consume, so the enforcement and the list filter can never diverge. (3) A new **`mcp.access_denied` action** fires before the throw — the MCP audit hook, mirroring `auth.access_denied`; like it, it cannot reverse the decision. Proven end to end: a `role=viewer` bearer token is refused `klytos_delete_page` with a JSON-RPC error object + **HTTP 403** over real HTTP, an owner bearer is allowed the same tool, an unknown role and an unmapped tool are denied, and `tools/list` for a viewer returns 19 tools without any destructive one — every denial proven to FAIL against the ungated code first (L-016).

## D-047 — MCP credentials carry a role, resolved from the credential, with an idempotent boot migration; unknown or absent role denies
- Date / phase: 2026-07-22 / Phase 5, Sprint 2 planning (user decisions 2 and 3, taken 2026-07-21)
- Decision: The MCP identity is built from the presented credential, not from a session. `token-auth.php` stops discarding the authenticated subject (the OAuth `user` is surfaced at `oauth-server.php:557` and dropped at `token-auth.php:228`) and surfaces an actor `{user_id, role}` to `server.php`; credential records gain a **role**. `createBearerToken()` takes an optional role (default `owner`). A single idempotent boot migration (the D-021 shape) backfills the installed base: **existing app-password and bearer-token records → `owner`** (recording what is already true, not a weakening), and an OAuth token → the role of the username it already stores. A credential that resolves to **no usable role, or a role the matrix does not know, DENIES** — the same fail-closed direction as `klytos_current_user()` after D-021.
- **Why "migrate to owner" is honest rather than a widening:** today every credential that can exist already operates as owner, because there is no per-call gate at all (NEW-02) and app passwords are structurally pinned to `config['admin_user']` (`auth.php:588-592`). Stamping the existing records `owner` records the status quo; it grants nothing that is not already held. What the change adds is the *ability to mint a lower role* going forward — which is what makes the gate in D-046 able to reduce power at all.
- **The residual gap is stated plainly, not papered over (user decision 3):** an existing bearer token carries no user field (`auth.php:469-475`), so after migration it is an **unattributed credential holding owner**. That is recorded as its own finding with a trigger in `docs/reference/mcp-authorization.md` (slice 4) rather than implied away — the honest limit is that migration cannot attribute a credential the product never attributed.
- **Per-role application passwords stay out of scope (L-014 framing):** app passwords are structurally owner-only until the **NEW-11** authentication slice lets a non-`admin_user` account exist and authenticate; minting an app password at a lower role is that slice's work. So the sprint's genuine end-to-end proof is a **`role=viewer` bearer token** — the one credential mintable at a lower role today — denied a destructive tool over real HTTP.
- Verification required (not optional): the upgrade path is tested **from the real previous version** (`scripts/dev/upgrade-test.sh`, real v0.30.1), asserting existing credentials resolve to `owner` after the migration and that re-running boot does not double-apply it.
- Alternatives rejected (and why): **leave credentials role-less and gate only by a global** (no way to express a lower-privilege credential, so the gate can never reduce power — defeats the sprint's purpose); **migrate existing credentials to a low role** (breaks every live integration on upgrade, and misrepresents reality — they operate as owner today); **default an unknown role to `viewer`** (fail-open's cousin — a corrupted or plugin-defined role would silently gain viewer's surface; unknown must deny, matching D-021 and the fix NEW-02 demands of `chat-engine`).
- Supersedes: none. Prerequisite for **D-046**; mirrors **D-021**'s fail-closed-with-migration shape on the MCP credential axis.
- **Amended during slice 1 implementation, before commit — the app-password mechanism, not the outcome.** The Decision above said the migration stamps "existing app-password **and** bearer-token records → owner." In the code it is cleaner and DRYer to resolve the **application-password and OAuth roles from the user record** (via `UserManager::getByUsername()`) — exactly as this decision already specified for OAuth — and to stamp a role **only on bearer tokens**, which name no user and so have nowhere else to hold one. The outcome is unchanged: an existing app password still resolves to `owner`, because it is pinned to the admin user, who is the owner. The gain is one source of truth for a credential's role (the user record wherever a user exists), forward-compatible with per-user credentials under NEW-11 — the role follows the user automatically. So `migrateCredentialRoles()` touches **bearer tokens only**. Proven on a real upgraded install (`scripts/dev/upgrade-test.sh`: a v0.30.1 bearer token, role-less, is stamped `owner` at boot).
- **A footgun caught by the migration test, recorded because it is the transferable part (L-017):** the first `migrateCredentialRoles()` iterated `$tokensData['tokens'] ?? [] as &$stored`. Iterating the result of `??` **by reference** binds to a throwaway temporary, so the stamps never wrote back — the method returned a non-zero count while persisting nothing (which would have DENIED every pre-Sprint-2 bearer token). Caught only because the test asserted the **persisted role**, not the return value. Fixed by guarding the key and iterating the real array. The same pattern in the pre-existing `validateAppPassword()` silently drops the app-password `last_used` update — recorded as **NEW-29**, not fixed (adjacent, cosmetic; D-031's narrowing).
