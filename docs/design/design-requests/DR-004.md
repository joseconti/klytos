# DR-004 — Where does the sidebar's search form submit with JavaScript off?

Status: **drafted — not sent**
Raised: 2026-07-29, Phase 4 Step 4, stage 2 (the shell)
Blocks: one control. The rest of stage 2 is built and verified.
Related: D-073 (the same shape, at a larger scale), L-030

---

## What is missing

`SPEC/screens/template-shell.md` §1, "Search field", specifies:

> **Search field** — 30px, `⌘K` pill absolutely positioned right. Focusing it
> opens the command palette; it is a real `<input type="search">` in a
> `<form role="search">` that also works as **a plain search submit with JS
> off**.

Everything in that sentence is buildable except the last clause. A form that
submits needs a destination, and **no file in the delivery names one**:

- `SPEC/manifest.md` has no search-results screen among its 44 entries.
- `SPEC/navigation.md` §5 lists the seven entries with no nav home; none is a
  search screen.
- No `SPEC/screens/*.md` describes a results surface, and no template
  (`list-table`, `overview-stats`, …) is named as its host.
- `SPEC/interactions.md` describes the palette's behaviour with JS, not without.

## Why the build did not resolve it

This codebase has no admin-wide search surface to point the form at. The only
screen with a search parameter of its own is `logs.php`
(`$_GET['search']`), which searches log lines — pointing the shell's search
there would be inventing a product behaviour, not implementing one.

Phase 4 rule 2 is *do not invent* and rule 3 is *do not interpret*. Choosing a
destination is both. It is also the exact shape of D-073: a sentence that reads
as complete until you try to write the line, and the tempting fix is a plausible
guess nobody would ever notice was a guess.

## What was built meanwhile

The specified half is complete and verified:

- a real `<form role="search" aria-label="Search the admin">`
- a real `<input type="search">` with the `⌘K` pill positioned right
- focusing it opens the command palette
- the palette itself has full combobox semantics per `SPEC/accessibility.md` §5.11

The form carries **no `action`**, and submitting is suppressed rather than sent
somewhere arbitrary. With JavaScript disabled the field is therefore inert — an
honest gap, not a hidden one, and it is commented as such in
`installer/admin/templates/sidebar.php`.

## What is asked

One of these, whichever matches the intent:

1. **Name the destination** — a screen and its template, added to
   `SPEC/manifest.md` as an entry with a `SPEC/screens/*.md` file, exactly as
   §4 of `navigation.md` required of Guides before it could be a nav item.
2. **Name an existing entry** as the destination, with the query parameter and
   what it filters (e.g. "submits to entry 1, Pages, filtering by title").
3. **Withdraw the clause** — state that the search field is a palette trigger
   only and has no JS-off behaviour, and say what a person without JavaScript
   sees instead (nothing, a hidden field, or a plain link to a screen).

Option 3 is a legitimate answer and needs no new screen. What the build cannot
do is pick between the three.
