## The finding, in one sentence

`SPEC/screens/template-list-table.md` §1 says `grid-template-columns` **is per
screen**; `SPEC/manifest.md` records it for **entry 1 only**; and the two other
places that could supply it both point back at something else — so for twelve of the
thirteen list-table surfaces there is no column width anywhere in the delivery.

## The chain, quoted, link by link

1. `SPEC/screens/template-list-table.md` §1:
   > "Grid on the table elements, not on wrappers — exact rule in `SPEC/accessibility.md`
   > §2.1. **`grid-template-columns` is per screen**; `gap: 12px`; numeric and action
   > columns right-align"

   and §1's own opening contract:
   > "Specify once here. A consumer screen only records **its columns, its filters, its
   > empty sentence and its deltas**."

   Note what that sentence does *not* list: the widths. The template delegates them to
   the screen; the screen's recorded duty does not include them.

2. `SPEC/accessibility.md` §2.1, the mandatory-rules list:
   > "`.k-table tr{display:grid;grid-template-columns:…;gap:12px}`. **Column widths**,
   > gap, row padding and truncation are exactly as **the README's Table entry**
   > specifies — the visual result is byte-identical to the prototypes."

3. The README's Table entry, in full, where the widths would be:
   > "`tr{display:grid;grid-template-columns:…;gap:12px}`"

   An ellipsis. The README's Table entry specifies the gap, the roles, the truncation
   rule, the alignment rule and the selected-row treatment. It does not specify a
   column width, for any screen.

So §2.1 forwards to the README, the README forwards to nothing, and the template
forwards to the screen — where, for twelve screens, nothing was written.

## The second gap, which is smaller but the same shape

Three of the surfaces above have **no column list either** — not just no widths:

- **28 Licence** — "Activated domains (list-table)" is named as a card and its columns
  are never enumerated.
- **35 Updates** — "Plugin updates (list-table with a batch action) · History
  (list-table with rollback)" names two tables and enumerates the columns of neither.

Every other list consumer in the manifest carries a `Columns:` line. These three are
the exceptions, and a table with no columns cannot be built at all.

## Why the prototypes cannot be used to fill this in

`accessibility.md` §2.1 says the visual result is "byte-identical to the prototypes",
which reads like an instruction to take the widths off the drawings. It does not work,
and the reason is not a rounding difference — **the prototype tables have different
columns from the manifest's own column lists.** Three checked in full:

**Entry 1, Pages.** `Klytos Admin - Screens.dc.html` draws
`28px 1fr 240px 110px 120px 110px` — **six** tracks. The manifest specifies **seven**
columns and gives seven tracks (`28px 1fr 116px 132px 96px 132px 44px`). Two normative
sources, different values, on the one screen where both exist. We are building the
manifest's, because it is the SPEC and it is screen-specific — but it means the
prototype is demonstrably not a reliable source for the other twelve.

**Entry 5, Users.** The prototype draws `1fr 220px 110px 110px 130px 90px` over cells
`{{u.name}}+{{u.username}}` · `{{u.email}}` · `{{u.role}}` · `{{u.status}}` ·
`{{u.lastLogin}}` · `more_horiz`. The manifest specifies: checkbox · **Name + email**
(row header, email in mono) · Role · **2FA** · Status · Last login · actions. The
prototype has **no checkbox column**, has **no 2FA column**, and gives **email its own
column** where the manifest folds it into the row header. The column sets are not the
same set at different widths; they are different sets.

**Entry 15, Plugins.** The prototype draws `1fr 90px 150px 100px 110px 130px` over
cells name+desc · `{{p.version}}` · `{{p.author}}` · **`{{p.license}}`** ·
`{{p.state}}` · `{{p.action}}`. The manifest specifies: checkbox · Name + description ·
Version · Author · Status · actions. The prototype has **no checkbox** and carries a
**Licence column the manifest does not list**.

Mapping a six-track drawing onto a seven-column specification requires deciding which
track becomes which column and inventing the width of the ones that were never drawn.
That is inventing a layout — Phase 4 rule 2 — and inventing it inconsistently across
twelve screens, which is worse than inventing it once.

## What the build has done in the meantime, stated exactly

- **Nothing was guessed.** No width was derived, interpolated, copied from a
  neighbouring screen, or set to `auto` and called faithful.
- The shared table layer (`.k-table` grid mechanics, roles, caption, selection, sort,
  pagination, empty/error/success rows, the responsive rules, `.k-table-scroll`'s
  containing block) is **fully specified** by `template-list-table.md` §§1–4 and
  `accessibility.md` §2.1 and is not blocked by this.
- **Entry 1, Pages, is fully specified and is being built**, using the manifest's
  seven-track value over the prototype's six.
- No other list screen has been written.

## What Design needs to deliver

1. **A `grid-template-columns` line per list-table surface**, in `SPEC/manifest.md`,
   alongside the existing `Columns:` line — for entries 5, 15, 24, 27, 28, 30, 32, 33,
   34, 35 (both tables), 36, and 14 when its slice comes. Same form as entry 1's, with
   one track per column in the `Columns:` list, including the 28px checkbox track where
   the screen has a checkbox column.
2. **A column list for the three surfaces that have none**: 28 Licence (activated
   domains), and 35 Updates (plugin updates, and history).
3. **Please also reconcile entry 1 against its own prototype**, or state which of the
   two is right — we have taken the manifest's, and if that is wrong it is wrong on the
   one screen we have already built.

If the intended answer is a **rule** rather than thirteen values — for example "the row
header takes `1fr`, numeric columns 110px, an actions column 44px, a checkbox column
28px, everything else 130px" — that is equally good and shorter to deliver, as long as
it is written down normatively. We will not derive that rule ourselves from thirteen
drawings.

| Manifest entry | List-table surface | Columns listed | Widths | Phase 4 scope |
|---|---|---|---|---|
| 25 | Consent — cookie audit | **no** | **no** | in scope — **built anyway, see below** |

**Why this one was built while the other twelve wait, on the user's explicit decision.** DR-006's
own reasoning for refusing the prototypes is quoted verbatim above: the prototypes' tables carry
**DIFFERENT COLUMNS**, not the same columns at other widths, so nothing in them can substitute for a
manifest value. **On entry 25 there is nothing to differ from** — the manifest names no columns at
all — and three independent sources agree instead:

- `screens/Klytos Admin - Screens 4.dc.html` draws `grid-template-columns: 170px 120px 90px 1fr`
  over **Cookie · Type · Duration · Description**;
- the shipped `consent.php` already renders those same four headings;
- nothing in `SPEC/` contradicts either.

So taking them is reading the delivery rather than deriving a value, which is the distinction this
request exists to protect. It is recorded as `BUILD-SPEC.md` §5.9 adaptation 33 and the screen is
built, driven and shipped.

**What is still asked of Design:** record the four columns and their widths for entry 25 in
`SPEC/manifest.md` normatively, exactly as entry 1 already carries its seven tracks — so the value
the build is using stops being an inference from a drawing and becomes the SPEC's own. If the
intended columns differ from the four above, say so: the screen is one block away from following
whatever is stated.

**Nothing else about this request changes.** The twelve surfaces above remain blocked, no width was
derived or interpolated for any of them, and entry 1 remains the only one the manifest records.

## ADDENDUM — 2026-08-29 (D-113), added AFTER this request was sent

**A fifteenth blocked surface, found the way none of the others were: by looking at a screenshot.**

Manifest **entry 18 (Agent payments)** carries three tables that this request's table never
enumerated — the revenue chart's data table (`Date` · `Revenue` · `Requests`), *Top pages*
(`Page` · `Requests` · `Amount`) and *Top bots* (`Bot` · `Requests` · `Amount`) — plus a two-column
provider key/value table. §18 records **no columns and no widths for any of them**.

**What that cost, concretely.** `.k-table` is `display: grid`, and `klytos-components.css` gives
`tr` a deliberate `grid-template-columns: 1fr` fallback precisely so a screen that forgets is
"visibly wrong rather than subtly wrong". Entry 18 forgot: all three tables rendered **one cell per
row at every width**, shipped in `d71a704`, turning a 1000px viewport into a **5731px** page. No
assertion could see it — the table was present, open and in the right DOM position, all of which is
true of a one-column table.

**Why the prototype cannot fill this one in either.** For entry 25 three sources agreed and the
value was READ. Here `Klytos Admin - Screens 3.dc.html` carries `x402Tables` as name/count/amount
ROWS with an icon per row — not as a grid with tracks. There is nothing to read.

**What the build has done in the meantime, stated exactly.**
`grid-template-columns: minmax(0, 1fr) max-content max-content` on the three-column tables and
`minmax(0, 1fr) max-content` on the provider table, declared on the screen and logged as
**adaptation 95**. The tracks are content-driven — the label takes the space, each number takes what
it needs — so no measurement is invented and nothing can disagree with a value Design has yet to
write. **It is replaced verbatim the moment this request answers.**

**One further question, which is Design's and not the build's.** The *Top pages* and *Top bots*
cards print their title **twice**: once as the card's `<h2>` and again as the table's `<caption>`,
which `SPEC/accessibility.md` §2.1 requires to be VISIBLE ("the table card's heading row, not a
screen-reader-only crumb"). One of the two is redundant. Which one should go — and if the caption
stays, what the card heading above it should say instead?
