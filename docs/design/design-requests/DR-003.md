## Gap 1 — 19 of the 35 glyphs the sidebar navigation uses are not in the delivered sprite

**Where expected:** `assets/icons/klytos-ui-icons.svg`, described by `SPEC/assets-index.md` §3 as
"one `<symbol>` per glyph the design uses", and named by the same section as the sidebar's icon
source ("**18px in the sidebar**"). `SPEC/open-questions.md` item 5 records the sprite as the
resolved answer to how icons ship.

**What the design draws.** Every prototype's `navGroups` array names its nav icons by Material
Symbols name. Taking the union across all six `screens/Klytos Admin - Screens*.dc.html` plus
`Copilot dock` and `Redesign`, the sidebar uses **35 distinct glyphs**.

**What the sprite contains.** 67 `<symbol>`s, ids `ks-` + the Material Symbols name — the list
enumerated in `assets-index.md` §3 itself.

**The intersection, computed rather than eyeballed:**

| | Count | Glyphs |
|---|---|---|
| Nav glyphs the design draws | 35 | — |
| **Present** in the sprite | 16 | `auto_awesome` `dashboard_customize` `data_object` `description` `extension` `imagesmode` `schedule` `sell` `smart_toy` `system_update_alt` `terminal` `toll` `tune` `verified_user` `webhook` `widgets` |
| **ABSENT** from the sprite | **19** | `account_circle` `category` `checklist` `cookie` `dynamic_form` `forum` `group` `menu_book` `monitor_heart` `monitoring` `palette` `perm_media` `policy` `preview` `receipt_long` `shield` `space_dashboard` `translate` `workspace_premium` |

Reproduce it:

```sh
grep -o 'id="ks-[a-z0-9_]*"' installer/admin/assets/icons/klytos-ui-icons.svg \
  | sed 's/id="ks-//;s/"//' | sort -u > /tmp/sprite.txt
cd docs/design/design-handoff/screens
for f in *.dc.html; do awk '/const navGroups = \[/,/^    \];/' "$f"; done \
  | grep -oE "(nav|item)\('[^']*', *'[a-z_]+'" | grep -oE "'[a-z_]+'$" | tr -d "'" \
  | sort -u > /tmp/navicons.txt
comm -23 /tmp/navicons.txt /tmp/sprite.txt     # → the 19
```

**Why this is a Design Request and not a build-side top-up.** `SPEC/assets-index.md` §3 does allow
"a glyph the sprite lacks is added as a `<symbol>` in the same geometry" — that rule is written for
the one-off case. Nineteen glyphs, covering the **primary navigation of every authenticated
screen**, is the delivery being incomplete, not a gap the build fills in passing. Drawing 19
Material Symbols Outlined paths on the 24 grid at 1.5px stroke is authoring visual assets, which
Phase 4 principle 2 forbids the build from doing. The two alternatives are worse and neither is
taken: **substituting a present glyph** (`folder` for `perm_media`, `verified` for `shield`) changes
what Design chose, and **shipping a second icon set or a CDN font** is refused outright by build
rule 4 of `docs/BUILD-SPEC.md` §5.0.

Note for the record: `SPEC/open-questions.md` item 18 asked exactly this question for the Dashboard
("Does the Dashboard need a new glyph?") and answered it by **checking all eleven against the
sprite**. That check was never run for the shell.

**Needed:** the 19 glyphs above added to `assets/icons/klytos-ui-icons.svg` as `<symbol id="ks-…">`
in the same geometry as the existing 67 (Material Symbols Outlined 24 grid, `stroke-width: 1.5`,
round caps and joins, `fill: none`, `currentColor`), and `SPEC/assets-index.md` §3's enumerated
glyph list and count updated to match.

**Also please confirm or supply, in the same pass** — three shell controls whose glyph the design
never names, and which the build must not invent:

- the **"Navigation" drawer button** below 900px (`template-shell.md` §2) — a `menu` glyph is not in
  the sprite;
- the **"Expand navigation" button** at the foot of the 56px icon rail (§2);
- the **theme toggle** in the account row (§1 *Theme toggle*) — if it is icon-bearing, name the
  glyph for each state; if it is text-only, say so and no glyph is needed.

**Deliver into:** `assets/icons/klytos-ui-icons.svg` + `SPEC/assets-index.md` §3.

## Gap 2 — there is no normative specification of the sidebar navigation itself

**Where expected:** `SPEC/screens/template-shell.md` (which specifies the sidebar's *states*,
responsive behaviour and accessibility, and explicitly says geometry/colour/type come from the
README) and `README.md` §*The shell*.

**What exists.** The README names the eight groups in one sentence — "Nav groups used across the
design: **Site · Content · Design · Intelligence · Monetisation · Compliance · System · Account**.
Plugins may add one entry" — and nothing else. Which of the 44 manifest entries belongs to which
group, in what order, with what label, glyph and count, is specified nowhere.

**What the prototypes show, and why they cannot substitute for a specification.** Each prototype
carries its own partial `navGroups` — a different subset per file, evidently chosen to suit the
screens that file draws:

| File | Groups it draws |
|---|---|
| `Screens.dc.html`, `Screens 2`, `Copilot dock`, `Redesign` | Site · Content · Design · Intelligence · System |
| `Screens 3` | Site · Content · Design · Intelligence · **Monetisation** · System |
| `Screens 4` | Site · Content · Intelligence · **Compliance** · **Account** |
| `Screens 5` | Site · Content · Design · **Monetisation** · System |
| `Screens 6` | Site · Content · Design · System |

No file shows all eight groups, and the union is not self-consistent:

- **`Blocks` contradicts itself.** It sits under **Design** in `Screens.dc.html`, `Screens 2`,
  `Copilot dock` and `Redesign`, and under **Content** in `Screens 3` and `Screens 6`. The build
  cannot pick the majority reading — that is interpretation, which Phase 4 rule 3 forbids.
- **`Guides` (Intelligence, count 16) is not a manifest entry.** There is no Guides screen among the
  44, and no `SPEC/screens/` file describes one. In this codebase the 16 guides are an MCP surface
  (`installer/core/guides/`) with no admin screen at all — so the nav links somewhere that does not
  exist on either side.
- Several in-scope screens never appear in any prototype's nav (for example **Webhooks** appears
  only in `Screens 4`, under *Intelligence*, while `Screens 3` puts `Health` and `Terminal` under
  *System* and omits Webhooks entirely), so "the union of the prototypes" is not a complete list
  either.

**Needed — one normative sidebar specification**, delivered as a section of
`SPEC/screens/template-shell.md` (or a new `SPEC/navigation.md`, whichever fits the structure
better), giving:

1. The **eight groups in their fixed top-to-bottom order**, with the exact caption text.
2. Per group, the **ordered items**, and per item: the visible label (the design's own copy — note
   these already differ from the H1s: *Media* → Assets, *Connections* → MCP), the `ks-` glyph, the
   manifest entry it links to, and whether it carries a count and of what.
3. The **resolution of `Blocks`** — Content or Design, one answer.
4. What `Guides` is: a screen that must be added to the manifest, or a nav item to drop.
5. Where the entries with **no nav home** live — Page editor (2), Verify (11), Setup wizard (17),
   Post type (39), Block data (40), Template preview (42), and the *States* specimen sheet (16):
   reached only from their parent screen, or nav items in their own right.
6. Where a **plugin's one entry** lands (the README says "Plugins may add one entry" without saying
   into which group), and what happens when several plugins are active — this project ships two and
   supports arbitrarily many.
7. What the item shows when the person **lacks the capability** for a screen: hidden, or shown
   disabled with the reason (the shipped admin hides it; `template-shell.md` §1 does not say).

**Deliver into:** `SPEC/screens/template-shell.md` (+ `SPEC/manifest.md` if `Guides` becomes a
screen).
