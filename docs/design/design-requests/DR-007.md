# DR-007 — the console stream's own geometry fails two rules the delivery states elsewhere

Status: **drafted** — 2026-08-09. Not sent: sending is the user's call, and the
ready-to-paste prompt is the last section of this file.
Raised: 2026-08-09, Phase 4 Step 4, stage 4 — manifest entry **41 (Logs)**, found by
DRIVING the built screen per state in both themes, not by reading the delivery.
Blocks: **nothing structural.** Entry 41 is built, driven and shipped; the two
findings are excluded from its automated accessibility pass **by selector**, each
carrying its measured ratio and this DR's number, and the real measurements are
pinned by tests so a regression still fails while this request is open.
Affects: every console-stream consumer — **23 Terminal, 22 Health's log panel,
24 Webhooks' payload, 40 Block data** — because both findings are properties of the
template, not of Logs.
Related: DR-005 (the same shape one layer up: pairs the delivery specifies, composed
in a way its 72-pair audit does not include), L-030, L-032.

## Gap 1 — a stream line cannot be a 24px target, and §7 says it must be

`SPEC/screens/template-console-stream.md` §1 sets the stream in `--type-code`:

> "stream — card, `--fondo-ventana` panel inside, mono `--type-code` (12px/19px)"

and §2 makes each line an interactive control on this screen:

> "Individual lines are focusable **only** where selecting a line does something
> (Logs: opens the detail panel); there they are `<button>`s spanning the line, with
> the line's text as their name."

`SPEC/accessibility.md` §7 then states the target rule, its table of every element in
the admin, its two exceptions, and this closing sentence:

> "Two documented exceptions, both explicitly permitted by 2.5.8: **inline links in
> running text**, and **the drag handle** in reorderable lists… **No other exception
> exists. If a build produces a smaller target, that is a defect.**"

A line is 19px tall in its constrained dimension, and neither exception covers it.
Measured on the built screen: `target-size` reports every line at 16px of safe space,
and `target-offset` reports the same failure from the other side — the neighbouring
line is 19px away, so no 24px circle around a line is undisturbed.

**`.k-hit-24` cannot resolve this, and that is the point.** §7's own mechanism —
"the visual sizes do not change, the hit areas do, via a 24 × 24 pseudo-element" —
works everywhere else because the rows are already ≥ 24px apart (checkbox rows,
table rows at 40–48px, the 24px breadcrumb row). Stacked 19px lines leave nothing to
centre a 24px target in: enlarging one line's hit area only moves the overlap onto
the line above it.

**The build has not chosen between the two rules, and will not.** The line is drawn
at the specified 19px and the finding is registered here.

### What we are asking

Which of these is the design's answer? Any of them is buildable; choosing one is not
the build's call.

1. **A documented third exception in §7** — "a console-stream line" joins the inline
   link and the drag handle, on the reasoning that the stream is content-density
   territory in the same way §3 already makes it the one permitted horizontal-scroll
   surface. If so, please add it to §7's exception list in words, so the next
   console-stream consumer does not re-raise this.
2. **A line height that meets 24px** — which changes `--type-code`'s line-height for
   the stream, or adds a stream-specific one. This costs roughly a quarter of the
   lines visible in the same 60vh and changes the density of every console surface.
3. **Selection stops being per-line** — the detail panel is opened another way (a
   single "inspect" control, a keyboard-only affordance, an expandable row), which
   removes the target entirely rather than resizing it.

The copy affordance §2 puts at the right of each line has the same constraint and the
same answer, whichever it is: it lives in the 19px row.

## Gap 2 — the selected line's colours are below AA, in both themes

§2 specifies the selected state:

> "**Selected line** (Logs) — `--fila-seleccion`, `aria-pressed="true"`, detail panel
> populated with `<h2>` naming the event."

and §1 specifies the stream's text:

> "keys and structure `--texto-sutil`, values `--texto-secundario`, the one line that
> matters `--color-acento`."

Composed — which is what the screen does the moment a line is selected — those pairs
measure, read out of the browser on the real screen with the theme baked in before
first paint:

| Composition | dark | light | AA |
|---|---|---|---|
| `--texto-secundario` on `--fila-seleccion` over `--fondo-ventana` | **3.61:1** | **3.83:1** | ✗ 4.5 |
| `--texto-sutil` on the same | **3.37:1** | — | ✗ 4.5 |
| `--texto-secundario` on `--fondo-ventana` (unselected line) | 5.80:1 | **4.46:1** | ✗ light — **this is DR-005 gap 2**, arriving on its third surface |
| `--sobre-tinte-peligro` on `--tinte-peligro` over `--fondo-ventana` (ERROR line) | 5.35:1 | 4.53:1 | ✓ |

**This is not the delivered audit being wrong.** All 72 declared pairs were
recomputed at the Phase 4 gate and 72/72 agreed (`docs/BUILD-SPEC.md` §1c). It is
L-030 one layer down again: an audit that proves each pair correct without asking
whether the set covers what the screens actually compose. The ERROR row is included
above precisely because it PASSES — the tinted lines are fine, so the finding is
specific and not a general worry about this screen.

**The build invented no colour.** It substituted nothing, it did not "improve" a
token, and it did not disable a rule: the affected elements are excluded from the
axe pass by selector, and `tests/E2E/logs.spec.js`'s
*measures the pairs DR-007 asks about* records the real ratios and fails if they get
worse.

### What we are asking

What should a selected stream line paint its text in? `--fila-seleccion` is a 12 %
(light) / 24 % (dark) tint of the accent, so the options the delivery's own vocabulary
offers are a `--sobre-tinte-*` for the selection tint (none exists today), a heavier
text token on the selection, or a selection expressed as something other than a
background — §2's own bar-and-tint treatment for the ERROR lines is one shape that
already passes.

---

## What the build did meanwhile, so nothing here is a surprise

- Entry 41 is complete and driven: 30 browser tests over every state in both themes.
- Both gaps are excluded **by selector**, never by disabling a rule globally; every
  other element in every state is still checked, and a NEW defect on the same
  components still fails.
- `target-offset` is filtered from the result rather than disabled, because axe 4.12.1
  does not accept that id in `rules`. Same judgement, different mechanism, stated in
  the spec file.
- The measured ratios are pinned as floors, so an open Design Request cannot quietly
  become a licence to regress.
