# DR-013 — The Tasks screen counts two things the product cannot know, and never says how the list is grouped

**Status:** drafted 2026-08-11 · **NOT SENT** — sending is the user's call
**Raised by:** D-111 (Phase 4 Step 4, stage 7 slice 2 — manifest entry 13)
**Blocks:** nothing. Entry 13 is built with the facts the product holds.

## Gap 1 — *Due this week* and *Overdue* have no data source

`SPEC/manifest.md` §13 gives the screen four stat cards:

> - Stats: Open · Due this week · Overdue · Done (30d)

and one delta:

> - Delta: task state is a word plus a glyph; "Overdue" is never red alone.

**A Klytos task has no due date.** `TaskManager::create()` writes exactly
`id`, `page_slug`, `css_selector`, `description`, `priority`, `status`,
`created_by`, `assigned_to`, `created_at`, `updated_at` and `completed_at`, and
`update()`'s allow-list adds nothing. There is no due field anywhere in the
tree — not in the manager, not in storage, not in the MCP tools that create
tasks, and not in the front-end review widget that is the other way a task
arrives.

So two of the four cards would be numbers nobody measured, and the delta
protects a state that cannot occur. **This is not a column width or a missing
label: it is a product capability.** Adding due dates means a field, a writer, a
validator, an MCP surface, a sort order and a notion of "week" in the reader's
timezone — a slice with its own decisions, not a card.

## Gap 2 — the list is "grouped" and the axis is never named

> - Body: grouped task list — each task is a `<li>` with a title, a source
>   ("raised by System integrity"), and its action

**Grouped by what?** The product offers two candidate axes and the manifest
picks neither:

- **status** — `open`, `in_progress`, `completed`, `dismissed`;
- **priority** — `low`, `medium`, `high`, `urgent`.

The build took **status**, for two stated reasons: the delta itself says "task
*state* is a word plus a glyph", and the filter chips already select on status,
so grouping on the same axis gives one heading per group instead of a heading
that repeats the chip the reader just clicked. **That is a reading, and a
reading is exactly what Phase 4 rule 3 says to ask about rather than keep.**

## Gap 3 — the source line has nothing behind it

The example is *"raised by System integrity"*. A task records `created_by`,
which is a **user id**, and nothing anywhere records a *subsystem* as the origin
of a task. The line is not rendered; the row shows the page the task is on and
when it was raised, both of which are real.

## What the build did

Three stat cards — **Open · In progress · Done (30 days)** — every one a fact the
product holds. *In progress* is a shipped status this screen has always drawn; it
is built rather than dropped, and it is also what keeps the row inside
`template-overview-stats.md` §1's floor of three columns. The grouped list, the
badges (a word plus a glyph, never a colour alone), the filters and §13's
good-news empty state are all built as specified.
