# DR-005 — Three specified colour pairs measure below WCAG 2.2 AA in compositions the contrast audit did not cover

Status: **sent** — 2026-07-29. Drafted 2026-07-29 (D-078); the user's decision to
send it was taken at the start of stage 4, before the first list screen was built,
because stage 4 renders gap 1 on every one of them.
Raised: 2026-07-29, Phase 4 Step 4, stage 3 (the component layer)
Blocks: **nothing structural.** All twelve components are built and driven; three
elements are excluded from the automated accessibility pass by name until this
resolves, and every other element in every state passes at AA in both themes.
Related: D-069 §1c (the 72/72 contrast recomputation), L-030 (a gate that proves
an artifact is correct and never asks whether it covers what the screens compose)

---

## What this is NOT

It is not a claim that the delivered audit is wrong. `SPEC/color-contrast-audit.md`
declares 72 pairs; **all 72 were recomputed independently at the Step 1 gate and
72/72 agreed within ±0.06** (`docs/BUILD-SPEC.md` §1c). That arithmetic stands and
is not reopened.

The finding is about **coverage, not correctness**: the audit measures each pair on
*a* surface, and three of the compositions the screens actually build were never
among them. Every ratio below was measured in Chromium, on the real stylesheet
chain, in both themes, with the WCAG relative-luminance formula applied to the
composited background — not read off a table.

This is the same shape as L-030 one layer down. There, the gate proved the sprite
was intact and never asked whether it contained the glyphs the screens draw. Here,
the gate proved every declared pair was correct and never asked whether the
declared set covered every pair the screens compose.

## Gap 1 — a semantic badge inside a selected table row

**Where.** Any `list-table` screen. `template-list-table.md` §2 sets a selected row
to `--fila-seleccion`; `SPEC/accessibility.md` §2.1's own example markup puts a
`<span class="k-badge k-badge--exito">Published</span>` in a row. Both are
normative, and the design's list drawings show exactly this.

**The composition.** The badge's 11 % / 19 % tint is drawn over `--fila-seleccion`,
which is itself the accent at 12 % / 24 %, over the card surface — a three-layer
stack. The audit measures a badge tint over an admin *surface*.

**Measured** (`--sobre-tinte-exito` on the composite):

| Theme | Composited background | Ratio | Needs |
|---|---|---|---|
| Light | `rgb(205, 227, 218)` | **4.44:1** | 4.5 |
| Dark | `rgb(55, 103, 84)` | **3.08:1** | 4.5 |

The same badge on an unselected row passes (5.12:1 / 4.53:1), and standalone it
passes comfortably (5.15:1 / 5.11:1). It is the selection tint that carries it
under, and dark is not marginal.

**What the build did instead of choosing.** Nothing. No colour was substituted.

**What Design needs to decide.** Any of these resolves it, and the build will
implement whichever is chosen without further interpretation:
1. A `--sobre-seleccion-*` set for badge text inside a selected row (the same
   move `klytos-admin.css` already made for text on a tint).
2. An opaque badge background inside a selected row, so the audited two-layer
   composition is restored.
3. A different selection treatment that does not tint the row behind a badge —
   a left marker, a border, an outline.

## Gap 2 — the code / payload block's specified text colours on `--fondo-ventana`

**Where.** Terminal, Logs, Health's log panel, Webhooks' delivery payload, Block
data's stored JSON — every `console-stream` consumer.

**What the delivery specifies.** `template-console-stream.md` §1: the panel is
`--fondo-ventana`, and "keys and structure `--texto-sutil`, values
`--texto-secundario`, the one line that matters `--color-acento`."

**Measured, light theme, on `rgb(240, 240, 242)`:**

| Role | Colour | Ratio | Needs |
|---|---|---|---|
| Keys / structure | `--texto-sutil` | 4.53:1 | 4.5 — **passes** |
| Values | `--texto-secundario` | **4.46:1** | 4.5 |
| The line that matters | `--color-acento` | **4.23:1** | 4.5 |

Dark passes for all three (5.80:1, 5.44:1, 7.64:1). So this is a light-theme gap,
and it is narrow — 0.04 and 0.27 — but 1.4.3 has no tolerance band, and the
0.04 case is exactly the kind that a later token nudge would silently deepen.

**Note on which surface.** `--texto-sutil` was introduced by `klytos-admin.css`
because `--texto-terciario` failed; it passes here at 4.53:1. `--texto-secundario`
was not part of that revision and is the value that now falls short on this one
surface. It passes on `--fondo-elevado` and `--fondo-contenido`.

**What Design needs to decide.** Either a derived tone for these two roles on
`--fondo-ventana` (the `--sobre-*` pattern again), or a different panel surface
for the code block.

## Gap 3 — `--color-peligro` on `--fondo-elevado` in dark

**Where.** Two places at once, which is why it is one gap and not two: a field's
error message (`template-record-form.md` §2 — "the message in `--color-peligro`")
and a destructive button (`README` "Button" — "destructive (danger text/border)"),
whenever either sits **inside a card**.

**Measured, dark theme:** `#E6685F` on `--fondo-elevado` `#2C2C2E` → **4.32:1**
(needs 4.5). The identical control on `--fondo-contenido` `#232326` measures
4.86:1 and passes, which is why this survived: the audit measured the darker
surface, and cards are the lighter one. Light theme passes at 5.39:1 on both.

Error text is where this matters most: `SPEC/accessibility.md` §6 requires the
error to reach the person through four channels, and colour is one of them.

**What Design needs to decide.** A `--sobre-elevado-peligro` tone, or a rule that
error text and destructive buttons take `--sobre-tinte-peligro` (`#EC8E87`) on
elevated surfaces — that value measures 5.04:1 there — or a card surface change.
The build has **not** applied any of these.

## What the build did in the meantime, stated exactly

- **No colour was invented and no normative value was overridden.** Where the
  delivery states a value, that value is what ships, failing ratio included.
- The three elements are excluded **by selector** from the axe pass in
  `tests/E2E/components.spec.js` (`KNOWN_DELIVERY_GAPS`), each carrying its
  measured ratio and this DR's number. Every *other* element in those sections is
  still checked, so a new defect on the same components still fails the suite.
  The rule itself is never disabled.
- This is recorded as `⚠ blocked on DR-005` in `docs/PROGRESS.md` and in
  `docs/BUILD-SPEC.md` §5.5 — **not** as a passing accessibility contract. Per
  L-031, the fraction that could not be verified is the fraction to suspect.

**Three other pairs found in the same pass were NOT sent here, because the
delivery already answers them** — recorded so the distinction is on file:
the selected chip's text, a tinted log line's message text, and a read-only
field's text. In each case `tokens/klytos-admin.css` states the governing rule
("text is NEVER painted in a raw semantic colour on top of that colour's own
tint") and the build applied it. Those are integration, not gaps.

## ADDENDUM — 2026-07-29, added after stage 4 built the first list screen

Building manifest entry 1 (Pages) put the filter chips on a surface the
component specimen never used, and both chip states fall under AA there. This
is added to DR-005 rather than raised as a separate request because it is the
same family, the same palette question, and the same reviewer — splitting it
would make Design answer twice about one decision.

**Where.** `template-list-table.md` §1 puts the filter row in `main`, above the
table card. `main` is `--fondo-ventana`, not a card — so a chip on a list screen
sits on the window background, while the component specimen drew it on
`--fondo-elevado`.

**Measured in Chromium on the real stylesheet chain, and recomputed
independently from the token hexes — axe and the arithmetic agree:**

| Chip state | Colour | Composited background | Ratio | On a card |
|---|---|---|---|---|
| Unselected | `--texto-secundario` `#6E6E73` | `--fondo-ventana` `#F0F0F2` | **4.46:1** | passes |
| Selected | `--sobre-tinte-acento` `#0C7166` | `--fila-seleccion` over `--fondo-ventana` → `#D5E3E3` | **4.46:1** | 4.76:1, passes |

Dark passes for both. This is a light-theme finding.

**The first row is not new — it is gap 2's pair on a second surface.** Gap 2
above records `--texto-secundario` on `--fondo-ventana` at 4.46:1 for the code
panel. It is the identical pair at the identical ratio, and it turns out to
govern every filter chip on every list screen as well. Whatever resolves gap 2
resolves this, which is worth knowing before choosing a fix: a change scoped to
"the code panel" would leave thirteen filter rows failing.

**The second row is new** — a chip's accent-on-tint text over the WINDOW rather
than over a card. It is gap 1's shape (a tinted element inside a tinted
container) one surface out.

**What the build did:** nothing. No colour substituted. Both chip states are
excluded by selector from the axe pass in `tests/E2E/pages.spec.js`, each
carrying its measured ratio, and the chips are re-scanned in a second test with
`color-contrast` alone disabled so every other rule still covers them.

**What Design needs to decide:** whether gap 2's answer is a token-level fix for
`--texto-secundario` (which would cover both the code panel and the chips) or a
surface-level one, and whether the selected chip needs the same
`--sobre-seleccion-*` treatment gap 1 asks for.
