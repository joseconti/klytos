# Design Request DR-002: specify the Klytos admin Dashboard

The handoff `design_handoff_klytos_admin/` passed its completeness gate and the build contract is
written. **Do not redesign or re-deliver anything that already exists** — the tokens, the shell, the
11 templates, the 41 screens, the assets and every SPEC file are accepted and must stay
byte-identical. This request adds **one screen**.

## What is missing

The admin's landing screen — the **Dashboard**, `installer/admin/index.php`. It is a shipped screen
and it is where your own `SPEC/screens/template-shell.md` §3 sends the sidebar brand link
(`<a class="k-brand" href="index.php">`), but it has no entry in `SPEC/manifest.md`, no template
assignment and no SPEC file. The only dashboard in the bundle is inside
`screens/Klytos Admin - Redesign.dc.html`, which `SPEC/manifest.md` explicitly marks as an earlier
exploration kept for reference and **not for build**.

## What to deliver

1. **A `SPEC/manifest.md` entry** in the same shape as the existing 43 — appended, with the other
   entries untouched: the screen's `<h1>`, its PHP entry point (`index.php`), its template, its
   data, and only its **deltas** from that template.
2. **A template assignment.** If the Dashboard is an `overview-stats` screen, say so and specify it
   as deltas from `SPEC/screens/template-overview-stats.md` — no new template file. If it genuinely
   needs a twelfth template, deliver `SPEC/screens/template-<name>.md` in the same shape as the
   existing eleven: anatomy, every applicable state (default, hover, focus, active, disabled,
   loading, empty, error, success), the four breakpoints, and accessibility.
3. **The screen's content, decided rather than implied:** what it actually shows on a site that is
   working, what it shows on a **brand-new site with no pages, no traffic and no transactions**
   (the empty state, which is the state most first-time users will meet), and what it shows when a
   subsystem is degraded.
4. **Its accessibility**, to the standard the rest of the bundle already meets: the H1, the heading
   and landmark structure, the name/role/state of anything interactive, and — if it carries a chart
   — the mandatory `<details>` data table pattern from `template-overview-stats.md` §4.
5. **Its glyphs**, from the existing 67-symbol sprite `assets/icons/klytos-ui-icons.svg`. If the
   screen needs a glyph the sprite lacks, add the `<symbol>` in the same geometry (Material Symbols
   Outlined 24 grid, 1.5px strokes, `currentColor`, `fill:none`) and say so — do not introduce a
   second icon set.

## What is a question for the user, not for you

If any of these is genuinely a product decision rather than a design one, **ask the user directly —
do not invent it:**

- Whether the Dashboard is a stats overview at all, or something else (a task-first screen, a
  copilot-first screen, a recent-activity screen).
- Which figures it leads with, given that Analytics, Tasks, Health and the x402 dashboard each
  already own a set of their own — the Dashboard must not become a fourth copy of the same numbers.
- Whether it exists at all: sending the brand link to Pages instead of a dashboard is a legitimate
  answer, and if that is the answer, say so explicitly and update `template-shell.md` §3's brand
  link so the delivery is self-consistent.

## Constraints, unchanged from the bundle

- Multi-page PHP, server-rendered, no SPA. Filters and navigation are links; writes are form posts.
- Both themes ship; neither is the accessible one.
- WCAG 2.2 AA is the floor, as `SPEC/accessibility.md` sets it.
- English, sentence case, impersonal, no emoji.
- 1440 × 976 is the design viewport; the four breakpoints in the template file are the contract
  below it.
- Never a hex and never a font size in markup — every value is a token.

## How to re-deliver

Re-deliver the **whole** `design_handoff_klytos_admin/` directory in the same structure, so it can
be installed as a wholesale swap. Everything outside the additions above must be **byte-identical**
to the current delivery — the re-delivery is diffed against it, and anything that moved outside this
request's scope is itself a new gap.

Option 3 above ("whether it exists at all") is the user's call and can close this request without
Design touching the bundle. If the user decides the Dashboard is dropped and the brand link goes to
Pages, that is recorded as a decision in `docs/decisions.md`, `docs/BUILD-SPEC.md` §5.1 records the
