# Design Request DR-001: complete the handoff for Klytos Admin

The build cannot start because the handoff has gaps. **Do not redesign anything that already works** —
the colour tokens, the shell, the component inventory, the screen set and the interaction model are
all accepted and should stay byte-stable. Only specify the items below, then re-deliver the updated

## Accessibility spec — BLOCKING

- **Missing:** `SPEC/accessibility.md` does not exist, and no screen carries accessibility notes. The
  README specifies a visible focus ring and a reduced-motion variant; nothing else.
- **Where expected:** `SPEC/accessibility.md` plus per-screen notes.
- **Needed:** the full accessibility contract. Klytos is committed to **WCAG 2.2 AA as the floor, EN
  301 549 and the European Accessibility Act**, for the admin panel *and* the HTML it generates, and
  its current admin measures ~20–25 % against that target — so this redesign is the moment it gets
  fixed, not a later pass. Specifically:
  - **Contrast pairs with measured ratios**, for both themes: body/secondary/tertiary text on
    `--fondo-contenido` and `--fondo-elevado`; every badge/chip text colour on its own tint
    (`--tinte-*` at 11 % light / 19 % dark); primary-button text (`--sobre-acento`) on
    `--color-acento`; the focus ring against both surfaces; disabled states.
    **`tokens/colors.css` says in its own header that some tones on the badge tint "quedan al límite"
    and refers to `guidelines/auditoria-color-y-contraste.md`, which this bundle does not ship.**
    Ship that audit, or ship the measured numbers here — and where a pair fails, change the token or
    the pattern and say which.
  - **Focus order and the visible focus indicator** per screen, including the sidebar → toolbar →
    content → status-bar order, and skip-to-content.
  - **Accessible name, role and state per component and per state** — button, badge, chip, switch,
    checkbox, radio, field, progress, stat card, the copilot dock, the command palette. A switch and a
    checkbox are different roles; say which each one is.
  - **Heading and landmark structure** per screen: one `h1`, the heading levels, and the
    `banner`/`navigation`/`main`/`complementary`/`contentinfo` landmarks with their labels.
  - **Target sizes** (WCAG 2.2 AA, 24 × 24 CSS px minimum) — the 20px badge, the 13px checkbox, the
    14px radio and the table-cell icons at 15px all need an answer, whether that is a larger hit area
    or a documented exception.
  - **Text scaling and forced-colors/high-contrast behaviour**, and the reduced-motion variant stated
    as a rule rather than a mention.
  - **Error identification that is never colour-only**, for fields and for the log/status screens.
- **Deliver into:** `SPEC/accessibility.md` + the relevant `SPEC/screens/*.md`.

## Table semantics — BLOCKING, and it is a question, not a correction

- **Missing:** the README says *"Table — CSS grid, not `<table>`, when columns are fixed-width."* A
  data table built from `display:grid` is not exposed as a table to assistive technology — no
  row/column relationships, no header association — unless explicit ARIA table roles are added, which
  the handoff does not mention. Every list screen in the admin (pages, users, plugins, transactions,
  options, logs, scheduled actions) is a data table.
- **Needed:** decide and specify one of: (a) a real `<table>` with the grid layout applied to it,
  (b) `display:grid` plus the full `role="table"`/`rowgroup`/`row`/`columnheader`/`cell` set, written
  out per component, or (c) a documented reason why these are not data tables. Whichever you choose,
  say it in `SPEC/accessibility.md` and in the Table entry of the component inventory. **Please do not
  simply answer "add ARIA" — specify the exact roles and where they go**, because a partial ARIA table
  is worse than a plain grid.
- **Deliver into:** `SPEC/accessibility.md` + the component inventory.

## Type tokens — BLOCKING

- **Missing:** the README's type table and the delivered `tokens/typography.css` disagree, and six of
  the ten roles the README names have no token at all.

  | Role | README | `typography.css` | |
  |---|---|---|---|
  | Body / table cell | `400 13px/17px` | `--type-body: 400 13px/18px` | conflict |
  | Secondary / hint | `400 11px/16px` | `--type-caption: 400 11px/14px` | conflict |
  | Section eyebrow | `600 10px/14px` mono, `0.06em`, uppercase | — | missing |
  | Table column header | as eyebrow | — | missing |
  | Nav item | `400 13px/16px`, active `500` | — | missing |
  | Toolbar title | `600 13px/16px` | — | missing |
  | Badge / chip | `500 11px/16px` | — | missing |
  | Numeric cell | mono `500 12px/17px`, right-aligned | — | missing |

- **Needed:** decide which value is canonical for the two conflicts, and add a token for every role
  the admin actually uses, so the build never hard-codes a size. The contract requires the SPEC and
  the delivered styles to agree.
- **Deliver into:** `tokens/typography.css` + the README's type table (make them identical).

## Token scope

- **Missing:** the token files are the generic PackDesk set, not scoped to Klytos.
  `tokens/typography.css` ships `--type-picking-linea` and `--type-picking-pedido` ("densidad XL de
  picking… en almacén") plus `--type-mono-pedido` / `--type-mono-importe` — another product's
  concerns. The files state neither their origin nor the target surfaces for this project.
- **Needed:** state the origin (inherited from the PackDesk design system, citing it) and the target
  surfaces this delivery covers, and separate what is Klytos's contract from inherited furniture the
  admin does not use.
- **Deliver into:** `tokens/*.css` headers + a `SPEC/design-tokens.md`.

## Per-screen specs

- **Missing:** 41 screens, no `SPEC/screens/<screen>.md`. States are gathered into one "States" screen
  rather than specified per screen, and the only responsive instruction is "recreate at 1440 × 976,
  then allow to reflow".
- **Needed:** one file per unique screen with **all applicable states** — default, hover, focus,
  active, disabled, loading, empty, error, success — and the responsive behaviour at each required
  breakpoint. If several screens share a layout, specify the template once and record each consumer
  screen with its data/variant in `SPEC/manifest.md` rather than repeating it.
- **Deliver into:** `SPEC/screens/*.md` + `SPEC/manifest.md`.

## Assets — logos and icons

- **Missing:** the 13 logo/icon files ship as **SVG only**. The contract requires every logo and icon
  in **both SVG and PNG** — PNG at intrinsic size plus the platform's required densities/sizes — and
  `klytos-favicon.svg` has no raster sizes.
- **Needed:** the PNG set, plus `SPEC/assets-index.md` listing every asset with its intrinsic
  dimensions, every delivered format, and its exact use and size.
- **Deliver into:** `assets/` + `SPEC/assets-index.md`.

## Assets — fonts

- **Missing:** `Geist-Variable.woff2` and `GeistMono-Variable.woff2` exist only under
  `screens/_ds/…/fonts/`, which the README says exists solely so the prototypes open offline. There is
  no `@font-face` against a final project path, no licence note, no acquisition block. The wordmark
  and lockup SVGs carry **live text**, so Geist Bold is a hard dependency of the brand assets.
- **Needed:** ship the font files at their final paths with the `@font-face` rules written against
  those exact paths, only the weights/styles actually used — or, if licensing prevents shipping them,
  the acquisition block per font: exact source, licence note, exact files, exact target path in the
  project tree. Also state whether the wordmark should ship with outlined text as a fallback.
- **Deliver into:** `assets/fonts/` + the delivered styles.
